# 车宠 · 手机 App 产品架构 V1.7

> **V1.7 变更（你装完 APK 提的三条，这一版就是对着那三条改的）**：「UI 不够精致、图标动效糙」「每个页面信息太乱、卫星不该是主场景，圆屏设备连接和 AI 对话才是」「借鉴了哪些开源项目 —— 我感觉都像你自己做的」。第三条我先如实回答：**到 V1.6 为止，代码里一行都没有抄开源项目**，附录 B 那份清单只是"看过、说得出为什么好"，所以它读起来像我自己做的 —— **因为它就是我自己做的**。这一版把这件事改成"该复用的真的复用"：
> **① 图标全部换成官方 `androidx.compose.material:material-icons-extended`（Apache-2.0，Material Symbols 的 Compose 端口）**，V1.6 之前那些自绘 vector 删掉。自己画的问题不在好看与否，在**撑不起语义**："卫星兜底""待发补录队列""电子围栏"这种名词，手绘的圆和箭头观众读不出来，官方图标集里 `SatelliteAlt` / `HourglassBottom` / `Security` 一读就懂。语义→图标只允许有一张表（`app/ui/MIcons.kt`），**加图标跟加颜色一样：先答得清它代表哪个语义**。可用性是实测出来的：那份 aar 的 classes.jar 里逐个核过图标名（名字猜错要到编译期才炸，来回几轮很贵）。
> **② 排版收口在"卡片要有共同的左边界"这一件小事上。** 之前图标单独占一行、标题在下一行，一屏六张卡读起来是六段"带图标的段落"，不是六张同一族的卡 —— 你说"排版显示存在问题"，根子就在这。现在图标列在最左、内容整体右移，标题全部从同一条竖线起排。**字号只放宽一处**：新增 `Display` 32sp，且只允许出现在首页那两个大数字块（`HeroStat`）上，正文/说明仍旧只有 15 / 12 两档 —— 放宽一处和放开一档是两件事。
> **③ 动效按 Material 3 motion 的口径来**（做法参考 nowinandroid / Tivi 的用法，都是 Apache-2.0）：统一收进 `Motion` 三档（160 / 260 / 420ms），换页用轻微推移 + 淡入淡出、状态变化用 `animate*AsState`、大数字换值用 `AnimatedContent`。倒计时环和进度条以前是 1Hz 一格一格抖的，现在插值抹平 —— **动一下眼睛才读得出"在倒计时"，而不是"数字变了"**。
> **④ 首页产品逻辑重排（你这条批评是对的，我照改）**：Tab1 现在只有两个主区 ——**圆屏设备连接**（在线几台、接入点、允许接入开关、`screen_id` 白名单就地加/删）和 **AI 主理人对话**（快捷问句 + 输入框 + 端点配置）；**卫星整体降成一条兜底横条**（相位、过顶剩余、展开完整链路卡/过境卡）。**唯一没降的是 SOS 长按入口** —— 它就在这条横条上，长按 3 秒、三段倒计时、松手可取消全都保留：安全件藏进二级页等于没有，这条 §5.1 的原话不动。首页卡片流里也不再重复出现过境卡（同一屏两张讲同一件事的卡，就是"信息乱"最实在的一种）。
> **⑤ AI 网关 `core/ai` 开工了**（V1.6 之前是"三个底座能力里唯一没动的一个"）：`SkillRegistry`（7 条内置技能，**关键词路由 + 结构化 JSON**，形状抄 digivita 已跑通的那套，见附录 D.2）、`PermissionTier` 五档（只读本机 / 读云端 / 写设备 / 出网 / 不可逆，默认只到第一档）、`OpenAiCompatProvider`（手拼 `/chat/completions`，12s 超时，端点没填齐就当没配）、`Heartbeat` 六条主动提醒规则（带冷却，不会刷屏）。**顺序是路由→取数→权限→生成，取数在生成之前**：模型拿到的必须是已经算好的事实；权限卡在中间，是因为拦下的那条**连上下文都不该发给别人的服务器**（"求救"这种句子发出去就等于把意图交给了端点）。文案红线也约束模型：输出里出现"已送达 / 救援已在路上"任一句，整条替换成不越界的说法。**端点不填时界面上逐条标「本机规则 · 未接模型」，不装作接了大模型。**
> **⑥ 出包 22.6 MB，比上一版重了 12 MB，重的就是那个图标 aar**（37.4 MB 的 classes.jar，debug 不 minify 时整包 dex 都进来）。release 开 R8 会按调用图裁到只剩用到的那些，所以**这不是必须付的代价，是 debug 包的代价**，写在 §8 R0 里而不是藏起来。`:core` + `:app` 单测 **196 条全绿**（新增 16 条 AI 网关测试），明文策略校验、`assembleDebug` 都过。
> **仍然不能吹的三件事**：① **这一版依然没有被眼睛看过** —— 这台机器没有 emulator、没有 system-image、`adb devices` 是空的，所以我只能保证"图标是官方的、左边界是一条竖线、动画有插值"，**不能保证它在你手机上是好看的**。你把截图发我，比我再改三轮有用。② **AI 只有骨架，没有真模型**：要接你们手上的 OpenAI 兼容端点（base URL + key + 模型名，首页那张卡里就能填），否则每一句回答都来自手机自己的状态。③ `firmware/screen/` 仍是空目录、这台机器仍无 ESP 工具链（pio / idf.py / arduino-cli 全无）—— 圆屏到货当天能做的仍然只有"用浏览器冒充它、把 App 侧验干净"。

> **V1.6 变更（补上 V1.5 欠的三条，并且这条链路第一次被一个真客户端连上过）**：这一版没有加新场景，做的是**把已经画在纸上的东西变成能跑的**。
> **① 设备总线建起来了**（`core/devices/DeviceBus.kt`）：圆屏、GT1005、手机定位、手环现在是同一个 `Device{kind, transport, link, since, detail, actions}` 表里的行，`Offline`（该在但断了）和 `Absent`（这台机器上没这个能力）是两种状态 —— 界面上"GT1005 离线"和"没有手环"从此不是同一句话。「我的 → 设备与底座」那张卡从桩变成了**真台账**：每台设备什么时候上线、当前链路档、离线多久，都是从总线读的；圆屏的 `screen_id` 白名单**在现场就能改**（加入 / 移出并立刻断开），不用重新装机。
> **② §5.3 硬要求第 2 条现在才算补齐**：连接层原先只到"进程内、Activity 之上"，**V1.6 起了前台服务 `DemoGuardService`**（`location|connectedDevice` 两类，API 34 分以上传 type —— 低版本传 `connectedDevice` 会当场抛异常）。「我的」里一个开关，打开后常驻通知钉住进程、锁屏后 1Hz 那一圈照跑，关掉就断开与圆屏的连接。**V1.5 那句"锁屏久了仍会被冻"到此作废。**
> **③ SOS 按 §3.1 的承诺做实了**：**长按 3 秒、三段倒计时、中途松手就取消**（倒计时不是装饰 —— 它把"误触"和"真要命"分开），发出后屏幕上一直有**「撤销这次 SOS」**。撤销走的是文案红线唯一出口 `SosCopy.cancelLine`，五档措辞按"星上收没收到 / 是否已交核心网"分别说，**任何一档都不说"已送达"**。同时把 `sos_cancel` 补进了 screen-link 契约：圆屏侧也能发起撤销，手机回 `sos_cancelled` 事件。
> **④ 用量页**（`usage` 卡）：长度等级、该等级下的字节上限、**按最坏口径折算出的单条可用载荷字节**、已交核心网/待发/丢弃/收回、额度压力条。订阅卡和它读同一个 `DemoEngine.usage()` —— 两个地方报两个数这种事，在演示现场是被抓住就完蛋的那种。口径未确认（§9 #12/#16）这件事直接写在卡上，不装作已经定了。
> **⑤ 这条链路第一次被真客户端跑通**（V1.5 之前只被单测证明过）：新增 `simulator/linkcheck.mjs`，用 Node 冒充圆屏连 8443，逐项断言 hello 有回执、3 秒内 ≥3 帧 state、必填字段齐、`command{sos_press}` 能逼出 event、`command{sos_cancel}` 能收到 `sos_cancelled`、同一 `event_id` 不重发（说明回执生效）、`bye` 立刻关。**8 项全绿。** 顺带查出一个只在现场会炸的行为：入站帧解不开时服务端**直接断连、一句话不说** —— 现在改成 `onContractError` 把原文和原因打进日志（`展示端帧解不开：…｜{"v":1,…}`）。另外补了 8 条**手写 JSON 字符串**的入站线格式测试（`ScreenLinkInboundWireTest`）：之前所有测试都是从我们自己编出来的消息往回解，**那是自证，不是对契约**。`:core` + app 单测 **180 条全绿**，出包 **10.6 MB**（提交 `f2a5579`、`2a67016`）。
> **仍然不能吹的三件事**：① **这套界面到今天为止还没有被任何一块屏幕看过** —— 这台机器没有 emulator、没有 system-image、`adb devices` 是空的；linkcheck 证明的是链路，不是版式。② §5.3 第 4 条 `feature-*` module 仍未拆（V1.5 说的时机不变）。③ AI 网关 `core/ai` 没开工，所以亲子 / 健康 / 分身三张卡还是带徽标的桩。**外加一条明天到场就会撞上的：`firmware/screen/` 到现在还是空目录，这台机器上 pio / idf.py / arduino-cli 一个都没有** —— 圆屏到货当天能做的只有"用 `screen.html` 在浏览器里冒充它、把 App 侧验干净"，屏自己的固件今天没有任何可烧的东西。

> **V1.4 变更（E.10 那 10 条代码改动全部落地 + 用字节码把厂商 SDK 重新对了一遍）**：两件事。
> **一是代码追平了文档**：删 `Gt1005Verbs`、字节管道、事件驱动上电会话、SOS 三态、TPI 周期任务、升级写锁、星历 `StarManager`、构建配置（minSdk 26 / RxJava3 / aar 进库 / 普通签名 / 明文按域名）、队列层与报文预算的运行时注入、`passthrough` 工程模式日志窗 —— **10 条全做完，`:core` 单测从 43 条涨到 158 条，`:app:assembleDebug` 出包 3.68 MB**（E.10 逐条标了实际落地形态，并把"还没做的两件"说清楚：物理口 UART/BLE 的真实现、`updateSOC` 真驱动写锁 —— **都等实物，不做投机代码**）。
> **二是把 SDK 从"读文档"改成"解字节码"（新增附录 E.12），结果文档错了四处**：① `EntityICI.getMaxMsgLength()` **返回的是等级原值（1~5），SDK 内部压根没有等级→字节的换算表**，所以那张换算表是我们的业务代码；顺带把 §9 #14 逼出一个更尖锐的问题 —— **模组按字节还是按 hex 字符拦报文，等级 1 下差一倍（90 vs 45）**（§9 #16，代码已按最坏口径做成一个开关）；② `CustomError` 实测**五个值**（文档只写四个，漏了 `TIMEOUT_ERROR`）；③ **`updateLocation()` 返回 `void`，而且 aar 里有 `EntityTPI` 却没有 TPI 监听器** —— "模组认了这条位置"在应用侧**不可观测**，所以 UI 只能说"最近一次推送于 N 秒前"，不能说"已同步"（§9 #17）；④ **`EntityDII` 没有任何位置字段**，"从模组读位置"这条路在 SDK 面上不存在（SDK 路线的 `readFix()` 直接返回 null，不编数）。另外三条集成期会炸的实测事实：`ModuleDataManager` 构造**包私有**、监听器**入参是 `java.util.function.Consumer` 而返回值是 rxjava3 `Disposable`**（两套生态混用）、**aar 里没有 `destroy()` 而资料包 jar 里有**（两个不同构建，§9 #18）。
> **一条方法论上的更正，比上面任何一条都重要**：**"照文档写代码"在这个 SDK 上已经被证伪**。从现在起我们以字节码 + 真机为准，文档只在能交叉验证时引用（§11 已加一条：向厂商要一份和 aar 同步的文档）。**§9 从 15 条涨到 18 条，其中 P0 从 3 条涨到 5 条。**

> **V1.3 变更（拿到时空道宇 SDK 后的一次大改，全部结论见附录 E）**：那份 SDK 我**已经从群里下载并解完**（两个 aar + 参考代码 + 28 页《通用数据接口规范 V1.0》）。它**推翻了三个假设**：① 协议是 **NMEA 风格 ASCII 语句**（`$CCSFQ,…*hh`，异或校验），不是二进制 → **我们的手写指令表 `Gt1005Verbs` 应该整张删掉，解析交给厂商 SDK**；② SDK **不做 IO**，只暴露 `send(byte[])/receive(byte[])` 让我们实现 → **UART 路线合法，BLE 只是官方 demo 的实现**，`UartModem` 不用推翻；③ 消息长度**分 5 个等级（≤90/200/230/430/1900 B）** → V2.0 方案里"1900B vs 90B"的矛盾**不是笔误，是等级差**，必须运行时读 ICI 决定。另外挖出两条会改变设计的硬事实：**SOS 的"卫星 ACK 只代表卫星收到，不代表核心网收到"**（写进文案红线），以及**规范里只有 GM1001（500 条/掉电保存/无超时）和 GM1003（50 条/掉电丢失/4 分钟超时丢弃）两颗型号，而我们一直说 GT1005** —— 这是现在最贵的一个待确认问题（E.6）。**还挖出两个我们此前完全没有的功能/约束**：**TPI —— 手机要把时间和经纬度反向喂给模组**（上电一次、之后 1~10 分钟一次，模组复位即丢，且**经纬度直接影响下行接收**，这是 §3.2 新增的一条 P0，E.5）；以及**两个 SDK 的线程模型完全相反**（基础通信回调全在子线程、星历必须主线程调用且主线程回调），这是集成期最容易炸的地方（E.8）。构建侧硬约束：**minSdk 提到 26、RxJava3、星历走明文 HTTP、禁止 platform 签名**。**§6 新增 6.1 两条红线，§8/§9/§11/§12 同步改写。**

## 0. 为什么要写这份

写这份文档时的 App（`apps/android`）只有一个页面：链路阶段、卫星状态、定位、SOS、一堆"模拟 xx"开关。它验证的是**卫星链路能不能通**，不是一个产品。演示时可以，用户拿到手会觉得"这 App 只会发 SOS"，是因为我们确实只做了发 SOS。**V1.5 已经把这一页换成了 §5 的四 Tab + SceneShell，V1.6 又补上设备总线、守护前台服务、SOS 长按与撤销、卫星用量页，V1.7 把首页重心从"卫星"改成了"圆屏 + 对话"**（五个场景、27 张卡、真数据是卫星那一路 + 设备台账 + AI 网关的状态类技能），所以这一段现在是**病因记录**，不是现状描述 —— 现状与仍未做的部分见 §8 R0 那一行：**骨架对了，但除卫星与设备台账那几路外全是带「示意数据 · 未接真源」徽标的桩，AI 有网关没有真模型，而且这套界面到今天为止还没被任何一块屏幕看过。**

这份文档把范围拉开：**App 是"车 + 宠物 + 孩子"三类随身对象的统一守护与用车服务入口，卫星只是其中一条兜底通道，圆屏是一个可以换底座的呈现外设。**

## 1. 产品定位

一句话：**把车里那个没人看的东西，变成一个一直有人看的东西。**

三条判据（任何功能上线前拿这三条量一下）：

| 判据 | 含义 | 反例 |
| --- | --- | --- |
| **离线可用** | 没网、没卫星时，本地已有的信息必须还能看能用 | 把车况页做成纯 H5，进地库就白屏 |
| **一条不丢** | 关键时刻（SOS、围栏越界、抛锚）的消息，链路断了要进队列、恢复后补发 | 断网就静默丢弃，只弹个 toast |
| **换底座不换 App** | 圆屏换成亲子底座、桌面底座，App 侧只改"投哪张卡"，不改业务逻辑 | 每加一个硬件形态就复制一套 Activity |

差异化不靠"有卫星"（华为、苹果都有），靠**卫星 + 车 + 宠物/孩子这三件事在同一台手机上、同一个账号、同一条兜底链路里闭环**。

## 2. 场景与用户

### 2.1 五大场景

| 场景 | 谁在用 | 高频时刻 | 低频但致命的时刻 | 谁付费 |
| --- | --- | --- | --- | --- |
| **车载**（用车养车 + 卫星通信） | 车主本人，副驾偶尔 | 上车看车况、停车看位置、保养提醒、违章/事故处理 | 地库失联、高速抛锚、无人区/海上、被盗 | 车主（订阅 + 流量包） |
| **亲子**（AI 育儿） | 家长设置、孩子使用 | 讲故事、问答、成长记录、接送途中陪伴 | 走散、被遗留车内、内容越界 | 家长（订阅，客单价高于车载） |
| **健康助手**（复用 digivita 设计） | 车主本人 + 家庭成员，**外部健康顾问**参与（digivita 里原称"主理人"，本轮改名以撇清医疗） | 体征同步、饮食运动打卡、主动提醒、周期复盘 | 疲劳驾驶 / 心率异常 / 久坐 / 老人走失 | 用户订阅 **+ 顾问侧服务费（B 端第二付费方）** |
| **综合**（数字分身 / A2A 社交） | 车主本人 + 家庭其他成员 | 消息代回、日程、行程分享、宠物/车的人设化互动 | — | 少量高粘性用户 |

优先级不是并列的：**车载是生存场景（有硬件刚需、有交付方），亲子和健康是变现场景（订阅意愿已被 Miko/BubblePal 验证，且健康有 digivita 的现成闭环设计），综合是叙事场景（讲得通、暂时不能当营收支柱）。**

### 2.2 用户画像（用来砍需求的）

- **P1 首购车主 30–45 岁，一二线，有宠物或 3–10 岁孩子**：愿意为"放心"付年费，不愿意为"炫技"付费。要的是"我看不到的时候你替我看着"。
- **P2 长途/越野/营运司机**：真会用卫星，会用存发队列，会算流量条数。付费点明确。
- **P3 家庭第二使用者（老人带孩子）**：不会配网络、不会授权。任何需要他操作的流程都是 bug。

## 3. 功能架构分层

分五层。**层与层之间只通过下面的接口说话，不允许跨层调用。** 这么分的原因是：卫星协议、圆屏固件、大模型这三样东西的变更速度完全不同，必须能把震荡关在各自的层里。

```
L5  账号与运营层    账号 / 设备绑定 / 家庭组 / 订阅与配额 / 埋点 / 远程配置
L4  呈现与形态层    手机 UI（Compose） / 圆屏投放（screen-link） / 语音输入输出
L3  场景服务层      用车养车 / 卫星守护 / 亲子陪伴 / 健康助手 / 分身与社交  ← 五个场景包
L2  能力层          链路状态机 / 消息队列 / 定位融合 / 设备总线 / AI 网关 / 规则引擎
L1  连接层          GT1005(UART/BLE) / 车辆(OBD/BLE/车机) / 圆屏(WebSocket) / 云
```

### L1 连接层

| 通道 | 现状 | 说明 |
| --- | --- | --- |
| GT1005 RS232 | `UartModem` + `LinePort` 已写，指令表待厂商确认 | **指令表目前是猜的**，到货前必须换成实测表 |
| GT1005 BLE | 未开始 | 协议文档未给，不排 P0 |
| 车辆 | 未开始 | 两条路：OBD-II 蓝牙适配器（后装，能读到 SOC/电压/故障码）或车机侧 API（前装，需要吉利开放程度） |
| 圆屏 | 已通，`:8443` WebSocket 服务，state 1Hz + event 带 ack | 明文 ws 是 D8 决策，量产前重评 |
| 云 | 未开始 | 只做三件事：星历、平台下行、账号同步。业务数据不默认上云 |

### L2 能力层（**底座，与场景无关**）

这一层是整个产品的重心，也是我们现在唯一真正动过的地方。

- **链路状态机** `LinkStateMachine`：CELL → PROBE → SAT → RECOVER，不对称滞回。SOS 绕过它。
- **可靠消息队列** `pending`：断链入队、恢复按序补发、`queue_pending` 直接给 UI 显示。**这是"一条不丢"的实现，所有场景共用。**
- **定位融合** `LocationMonitor`：GPS/网络/模块 GNSS 三个源，带 `source` 和 `hdop`。地库里模块 GNSS 是唯一来源，反过来车内金属屏蔽时手机 GPS 更好 —— 必须按精度选，不是按优先级硬排。
- **设备总线**（✅ V1.6 `core/devices/DeviceBus.kt`）：把"圆屏""GT1005""OBD 适配器""亲子底座麦克风"统一成 `Device`，带链路档、上线时间、能力描述、可执行动作。**没有它，每加一个硬件都要改一遍 UI** —— 现在加一台设备是往总线 `upsert` 一行。**电量还没进 `Device`**：GT1005 的电量在 SDK 面上没有对应读数（E.12），等实物或等厂商。
- **AI 网关 = Skill 注册表**（✅ **V1.7 已建骨架**，**直接沿用 digivita 已跑通的定义**）：一个 Skill = `触发关键词 + 结构化 JSON 输出 + 权限级别`，权限五档从 `READ_ONLY` 到 `SENSITIVE_DATA`（代码里是 `PermissionTier`：只读本机 / 读云端 / 写设备 / 出网 / 不可逆，**默认只到第一档**）。ASR/LLM/TTS 三家可换，统一超时与降级；**本地优先，不可用时明确告知，不假装在听**（V1.7 的形状：端点没填齐就退回本机规则并**逐条标来源**，绝不自称接了模型）。边界照 digivita 的结论抄：**不给模型无限制 Shell，未审批不执行破坏性动作，不靠提示工程防注入**（详见附录 D）。V1.7 落地的三条具体约束：① **顺序固定为路由→取数→权限→生成**，取数在生成之前，模型拿到的是算好的事实；② **权限拦下的那条连上下文都不发给模型**；③ **§6.1 的文案红线也约束模型输出**，命中禁用句整条替换。**仍然欠**：真模型端点与 key（等你给）、ASR/TTS 那条语音链路（在圆屏那侧，附录 A.3）。
- **规则引擎**（未开始）：围栏、超时、电量阈值、"孩子 20 分钟没说话"这类触发。**场景包只声明规则，不写 if**。

#### 3.4 健康助手（**复用 digivita 已跑通的设计，不从零想**）

digivita（大橙拾光）已经验证过一套双角色健康闭环，我们的任务不是重设计，是**把它接进车宠的传感器和场景里**。可搬的三件核心资产：**打卡闭环**、**Heartbeat 主动机制**、**健康主理人角色**（在车宠里更名 **健康顾问**，见下面红线第 2 条）。（细节与踩坑见附录 D）

| 模块 | 优先级 | digivita 现成资产 | 在车宠里怎么落地 |
| --- | --- | --- | --- |
| **体征同步**（心率/血氧/睡眠/步数） | P1 | 智能戒指 → `/api/device/sync` → `HealthIndicator` 表 | **必须走设备总线（L2）**，不能再起第二套蓝牙栈；戒指和 GT1005 在 `Device` 抽象里是同级设备 |
| **饮食/运动打卡** | P1 | AI 识别 → 自动 `approved`；手动 → 主理人审批 `pending→approved/rejected` → 连续天数 → 徽章 | **打卡/连续/徽章是亲子和健康共用的留存引擎，只做一次**，抽成 `feature-shared` 的规则 + 卡片 |
| **主动提醒 Heartbeat** | P1 | 每 2h 扫异常波动与未打卡，被动应答转主动服务 | **和我们的哨兵模式是同一件事** —— 统一成一个规则引擎的定时扫描，严禁写两套 cron |
| **体检报告 OCR + 周期复盘** | P2 | 拍照/上传 + OCR 方案、健康评估报告模板 | 权限档位 `SENSITIVE_DATA`，**默认不上传，本地解析** |
| **健康顾问（习惯督导，非医疗审核）** | P1 | digivita 主理人端的审批与群体分析机制 | 保留 B 端服务费这条线，但**责任边界是生活方式督导，不是医疗**（你的评论已定）；供给方后续由你这边对接，先按产品需要设计角色 |
| **驾驶疲劳 / 久坐 / 心率异常 × 车内联动** | P0 | 无（**车宠独有，digivita 没有**） | 连续驾驶时长 + 心率异常 → 提示靠边停车；**遗留车内**时孩子体征异常 + 车内高温 → 走最高级告警，同时打卫星 |
| 宠物健康档案（体重/用药/疫苗/驱虫） | P2 | 打卡与提醒模型可套 | 同一套规则引擎，换个数据模板；**别为宠物单开一个子系统** |

**边界（按你的评论定死：只做健康咨询，不涉及医疗）**：

1. **产品定位是"健康咨询/生活方式陪伴"，不是医疗服务**。所以：**不出诊断结论、不提药、不做疾病风险判断、不做医疗器械宣称**。AI 只做三件事：记录、趋势描述、生活方式建议（"最近三晚睡眠都低于 6 小时，建议把睡前一小时划出来"）。
2. **"健康主理人"这个角色在车宠里改名"健康顾问"**，职责限于生活方式与习惯陪跑，**不承担医疗审核签字**。digivita 那套"主理人审批打卡"的机制照搬，但**审批语义从"医学判断"降级为"习惯督导"** —— 这也让闭环不需要医疗资质就能跑。
3. 一句话不说清就可能出事的地方：**"心率高"可以是事实，"你可能有心律失常"绝对不能出现在文案里**。§5.2 的文案规范里要有一条禁忌词表（诊断/疾病名/药名/风险概率），代码层做输出过滤，不靠模型自觉。
4. 体检报告 OCR 只在本地解析、只呈现，**不做任何解读性结论**（要解读就转成"下次问医生时可以问这三条"）。
5. 数据边界不变：健康数据与儿童数据同档（§6），心率与体检报告默认留本地；digivita 底线**数据留平台、背书边界清晰**照抄。

## 4. 场景适配矩阵：圆屏换底座，App 怎么跟着变

这是"可拓展"的落点，也是 `dock_type` 这个字段真正的用途 —— 它不是用来打日志的，是**呈现层的路由键**。

| 形态 | 底座（**全部常供电，-B 不随盒带电池**） | 主屏内容 | 可用模块 | 输入 | 隐私档位 |
| --- | --- | --- | --- | --- | --- |
| **车载守护** | 车充 + 支架（点烟器/USB 供电，随车熄火即断电） | 环形状态盘 + 链路 + 一键 SOS | 卫星、车辆、围栏 | **触摸** + SOS 硬键 + 语音 | 普通 |
| **育儿陪伴** | 桌面 USB 供电（板载双麦） | 角色脸 + 对话气泡 + 时长 | AI 网关、成长记录、告警 | **双麦语音** + 触摸 + 家长手机 | **儿童档**（不录不存、仅本地） |
| **宠物看家** | 桌面 USB 供电 + 摄像头（后续） | 实时状态 + 喂食/活动统计 | 规则引擎、事件推送 | 触摸 + 按键 | 普通 |
| **桌面副屏** | USB 供电（"无底座"也要插线） | 时钟 + 日程 + 消息摘要 | 通知镜像 | 触摸 | 需显式授权，默认不投内容 |

> ⚠️ **形态表第一列本轮按实物评论改过：带外壳版（-B）不随盒带电池。** 所有形态都是"拖着线的"，**文案和演示讲解词里不能出现"摆哪都行 / 无线桌面屏"**（§8）。这不影响功能，但直接影响两种设计：① **待机/低功耗状态没有意义**（断电即关机，没有"电池模式下慢刷"这档），② **车载形态的"熄火后继续守 30 分钟"这种诉求做不到**，需要它就只能自行加电池或走 -G。

> 这块屏是 **466×466 圆形触摸 AMOLED，逻辑分辨率约 233×233，让出手势带后安全内容区约 165×165 逻辑像素 ≈ 4 行中文**（推导见附录 A.1）。所以每种形态**只允许一屏一个主信息 + 一个动作**，卡片里再套三行说明的设计在这块屏上一律作废。

实现要求（写进协议契约，不靠约定）：

1. App 侧 **不判断硬件型号，只读 `dock_type` + `capabilities`**，能力缺失就降级成一张说明卡，而不是空白或崩溃。
2. 卡片以"订阅"为单位投放：`{card_id, scene, min_priority, ttl}`，而不是 App 直接推像素。
3. 隐私档位由**底座 + 家长设置共同决定**，取更严的那个（详见 §6）。
4. **hello 要补屏幕几何**：`screen: {w, h, round, touch, ppi}`。行业做法是按「面板几何 + 可用输入设备 + 朝向」自适应，`dock_type` 单独一个枚举解决不了布局（附录 A.3 #1）。当前契约里 `dock_type` / `avatar_mode` 都只描述"人设"，不描述"能放几行字"。

## 5. App 信息架构与设计语言

### 5.1 导航

```
Tab1 首页（守护台）   —— V1.7 重排：两个主区（圆屏设备连接 / AI 主理人对话）
                          + 一条卫星兜底横条（SOS 长按就在这一条上，不降）
                          + 场景切换器 + 场景卡片流（可排序、可隐藏）
Tab2 车辆            —— 车况、寻车、养车工单、能耗
Tab3 家人            —— 亲子管控、成长记录、健康助手（体征/打卡/主理人）、共享对象
Tab4 我的            —— 设备与底座管理、主理人与模型（权限档逐条列）、订阅与流量包、隐私中心
```

原则：**SOS 和链路状态在 Tab1 首屏，不在设置里。** 一个需要三层菜单才找到的求救按钮，等于没有。
Tab 数量固定四个，**场景多了不加 Tab，靠 §5.3 的场景切换器切卡片集合** —— 加一个场景就加一个 Tab 的 App，半年后就变成十个 Tab 的迷宫。

**V1.7 把首页的"重心"换掉了，理由是这条**：到 V1.6 为止首页的主角是卫星链路，**那不是产品逻辑，是开发史** —— demo 是从那条链路长出来的，所以它占了第一屏。用户每天真正会碰的是两件："那块屏连没连上"和"我问它一句它答得对不对"。卫星于是退成一条兜底横条：**降的是位置，不是能力**（相位、过顶剩余、完整链路卡都能展开看到，SOS 长按入口原样在第一屏）。**这条重排不改 §5.1 那句"求救按钮不许藏"** —— 两句话不打架，因为藏起来的是"卫星状态的完整版"，不是"求救"。

### 5.2 设计语言（**简约但精美，得说清楚到底是什么**）

"简约精美"是形容词，不能照着开发。翻译成可执行的六条：

1. **一屏一个视觉重心。** 首页除了状态卡，其他卡一律折叠成一行摘要。想强调的东西超过一个，就等于都没强调。
2. **纯色底 + 一层语义色。** 底色只用两档（深底 `#0E1116` / 卡片底 `#161B22`），彩色**只用来表达状态语义**（绿=正常、黄=等待、红=SOS/告警、蓝=卫星链路），不做装饰色。这样"红"永远是真出事。
3. **字重和字号承担层级，不靠边框和阴影。** 只用三档字号（22 / 15 / 12），两档字重（Semibold / Regular），去掉卡片描边。**V1.7 放宽一处：新增 `Display` 32sp**，因为首页那两个主区各要当场回答一个大问题（"连了几台屏""还要多久过顶"），15sp 撑不起"一屏一重心"。**这一档只允许出现在大数字块（`HeroStat`）上、一屏最多两个**，正文与说明仍旧只有 15 / 12 —— 放宽一处和放开一档是两件事。
4. **图形优先，且形要有语义**：圆环=剩余、弧线=过顶窗口、点阵=队列条数、指北针=朝向。**图标一律用官方图标集，不自绘**：`androidx.compose.material:material-icons-extended`（Apache-2.0）。语义→图标只有一张表（`app/ui/MIcons.kt`），加一个图标要先答"它代表哪个语义"，答不上来就不该有 —— **和加颜色的规矩完全一样**。禁止用图标堆装饰。
5. **动效只用于反馈因果，且全部收进一个 `Motion` 对象**（160 / 260 / 420ms 三档，Material 3 motion 的时长口径，做法参考 nowinandroid 与 Tivi）：**内容换页**用轻微推移 + 淡入淡出，**状态变化**用 `animate*AsState` / `AnimatedContent`，**进出场**用短 tween；**不自创第四种**。1Hz 的倒计时和进度条必须插值后再画 —— 直接画成跳格，眼睛读出的是"数字变了"而不是"在倒计时"。不做加载骨架的闪烁。
6. **留白按 4 的倍数栅格**，所有间距取 4/8/12/16/24，不留"看起来差不多"的自定义值。

技术选型：

- **Jetpack Compose + Material 3**，深色为默认（车载夜间是主场景）；跟随系统动态取色只做点缀，主色板自己定，因为语义色不能随手机壁纸变。
- 组件不自己造：优先用官方 Compose 组件与现成 UI kit（开源清单见附录 B），**自己只维护"卡片流 + 状态徽标 + 倒计时环"三类**。
  **V1.7 起这条从"说法"变成"依赖"**：图标改吃官方 `material-icons-extended`（Apache-2.0，35.7 MB 的 aar），动效时长与换页转按 Material 3 motion 的口径。**组件层仍旧是我们自己那四个，没有套现成 UI kit —— 理由不是"自己写的更好"，是第 2 条那套底色和四色语义必须锁死，套任何一套现成主题都会跟着别人的 palette 走**（尤其"红只能等于出事"这一条，Material You 的动态取色会直接把它破坏掉）。
- 文案：状态用陈述句 + 下一步动作，不用形容词。
  - ✗ "信号不佳" → ✓ "蜂窝已断，卫星将在 3 分 12 秒后过顶，消息已进入待发队列（2 条）"
- 圆屏 UI 与 App UI **共享一套状态语义**（同一个 `StatePayload` 渲染），现在 `DemoRuntime.consoleText()` 已经是这么做的：手机和桌面用同一个渲染函数，避免两边说法不一致。这个做法要推广到所有状态文案。

### 5.3 场景怎么"快速切换"（这是你这次的要求，我给具体机制）

不要把场景做成 Tab 里的一组页面 —— 那叫切换目录，不叫切换场景。要做成**场景外壳（Scene Shell）+ 卡片注册表**：

```
SceneShell(当前场景)
  ├─ 读 SceneProfile：{ 主卡, 卡片顺序, 可用动作, 输入方式, 隐私档位 }
  ├─ 卡片来自全局 CardRegistry（各场景包只注册，不互相引用）
  └─ 切换场景 = 换一个 SceneProfile，不重建导航栈、不重新登录、不重连设备
```

四条硬要求：

1. **切换必须在一跳内完成**：首页顶部一个场景切换器（或左滑），不藏进设置。
2. **切换不改连接**：设备总线（§L2）在场景之外持有卫星模块/圆屏/车辆的连接，切场景时链路不能断 —— 这条只有把连接层抽到 Activity 之上才做得到。
3. **卡片按能力出现，不按菜单出现**：`SceneProfile` 声明需要哪些 capability，注册表里没有的卡就不渲染，也不报错。所以"车载场景没有心率设备"不是 bug，不需要为它写空状态页。
4. **每个场景包是一个 Gradle module**（抄 Now in Android 的 `feature/` 切分）：`feature-vehicle` / `feature-satellite` / `feature-kids` / `feature-health`，`app` 模块只做装配。**这样加场景不动主干，别人也不容易把跨场景的耦合写出来。**

工程目录（对应附录 B 的 fork 方案）：

```
app/                     装配 + 底部导航 + SceneShell
core/designsystem/       token、三档字号、四张卡的原语
core/model/              StatePayload / SceneProfile / CardDescriptor
core/link/               链路状态机 + 可靠队列（已有）
core/devices/            设备总线（V1.6 已建，见 §5.3）
core/ai/                 AI 网关（V1.7 已建骨架）
feature-vehicle/         用车养车
feature-satellite/       卫星守护
feature-kids/            亲子陪伴
feature-health/          健康助手（见 §3.4）
feature-home/            账号、订阅、隐私中心
```

- **没拆 `feature-*` Gradle module**（硬要求 #4）：现在是 `app/ui` 下的包边界 + 注册表 + 两条看护单测（扫 §6.1 禁用句、扫 `SceneProfile` 声明的卡是否全在注册表里）在守"场景不认识卡片、卡片不认识场景"。拆的时机定在**场景包开始分叉**之后 —— 具体说就是车辆总线和 AI 网关接进来、`feature-vehicle` 需要自己的依赖时。现在拆是空壳模块，只会让人把跨场景耦合写在 `app` 里。

- **硬要求 #2「切换不改连接」V1.6 才叫补齐**：连接层挂在 `Application` 上（V1.5）解决的是切 Tab / 转屏，**前台服务 `DemoGuardService`（V1.6）解决的是锁屏**。`foregroundServiceType="location|connectedDevice"`，type 参数按 API 分档传 —— 34 以下传 `connectedDevice` 会抛异常，这一条已经在代码里挡住。
- **硬要求 #1「切换在一跳内」V1.7 重排后仍然守住**：场景切换器从首页顶部挪到了两个主区下面，**但一次点击换走的仍然是整个 `SceneProfile`** —— 位置变了、机制没变。往下挪的理由是"一屏一重心"：之前切换器压在最上面，第一屏读起来像"先选行业再选功能"，而用户打开 App 要问的是那块屏和那句话。
- **AI 网关（`core/ai/`）V1.7 已开工**：五个文件、7 条技能、五档权限、一个 OpenAI 兼容 provider、六条主动提醒规则，16 条单测钉住行为。**它是纯 JVM 模块，不含任何 Android 依赖** —— 模型换供应商、端点换地址都不动 App 层；反过来 UI 也不绕过网关自己拼话（红线拦在 `AiGateway.guard` 里，模型输出也要过）。
- **还没拆的只有一件**：`feature-*` Gradle module（上面第 1 条）。

## 6. 数据、隐私与合规

这一块现在是空的，而它是亲子场景的**上线门槛**，不是加分项。

| 数据 | 采集 | 存储 | 上传 | 留存 |
| --- | --- | --- | --- | --- |
| 车辆位置轨迹 | 事件 + 定时 | 本地优先（加密） | 仅用户显式分享时 | 30 天滚动 |
| 孩子位置 | 仅告警所需 | 本地 | 不下云，除非触发 SOS | 7 天 |
| 孩子语音 | **默认不保存** | 会话内内存 | ASR 需要时明示，可选纯本地 | 会话结束即销毁 |
| 图片/仪表盘 | 用户主动 | 本地 | 否 | 用户控制 |
| **体征数据**（心率/血氧/睡眠/步数） | 戒指/手环同步 | 本地 + 加密云备份（可关） | 仅主理人服务开启时，按最小必要 | 24 个月（复盘要用） |
| **体检报告 / OCR 结果** | 用户主动上传 | **仅本地解析**（`SENSITIVE_DATA` 档） | 用户显式授权后传给指定主理人 | 用户控制，可一键抹除 |
| SOS 报文 | 含位置 | 必须落盘（断链时不能丢） | 卫星 | 直到**链路**确认。**注意：链路确认 ≠ 平台确认，见 §6.1 红线一** |

红线（来自近期监管动作，见附录 C）：儿童智能设备被点名的是**内容安全、防沉迷、语音数据滥用**三件事。所以：

- 儿童相关功能一律"关一档默认"：默认不录音、默认不联网、默认限时。
- 内容审核必须在链路里，不能指望模型自觉。
- 任何"分身/A2A"不得与未成年人角色自动互通。

> **本轮决策留档（你的评论）**：儿童语音/智能设备的**备案与认证路径本轮不做**（"暂不考虑备案认证相关"）。我按这个决定推进，但把风险写在这里，不在文档里粉饰：**这类义务通常是"产品卖到一定规模后被追溯"，不是"上线时有人拦你"** —— 所以真到规模化那天，这一条必须重新评估。可缓解措施（都很便宜，现在就做）：默认不录音、录音只在按住说话期间、语音不上传不落盘、家长端能一键关麦克风并看到状态。**做到这四条，将来补备案是补材料；做不到，是补架构。**

### 6.1 V1.3 新增：两条来自 SDK 的红线（不是合规要求，是能力边界，但违反它的代价和合规一样大）

**红线一：文案上绝对不允许出现"已送达"。** 规范 〔E.4〕 讲得很硬：**卫星返回的 ACK 只代表"卫星收到了这条报文"，不代表它到了核心网、更不代表对方收到了。** 而 SDK 把这件事做成了三个状态（〔E.7〕）：`COMPLETE` = 链路层完成、`COMPLETE + bundle==NO_ACK` = **发出去了但卫星没ack**、`FAIL + 失败码` = 根本没发。所以 SOS 的对外文案只能停在**"已发出 / 卫星已收到 / 未确认送达"**这三档，任何"救援已触发""对方已收到"都是虚假承诺。这条要同时改三处：App 文案、演示讲解词、以及**演示脚本里那句"你看它收到了"** —— 现场这么说，被懂行的人追问一次就收不住。

**红线二：明文 HTTP 与签名方式是发布硬约束，不是实现细节。** 星历 SDK 要求 `android:usesCleartextTraffic="true"` 才能拉轨道数据（〔E.8〕），同时**明确禁止使用 Android 系统签名（Platform Signature）**，否则"可能导致 SDK 无法正常运行"。我们的处理：① 不用全局明文，改用 `networkSecurityConfig` 只对厂商域名放行 —— **这需要向时空道宇要域名清单**（已进 §11）；② 签名方案锁普通签名，这和 §10.1 的"独立 App + 自有账号"是同向的，不额外付代价。

## 7. 商业化

对标结论（详见附录 C）：

1. **SOS 不能因欠费失效** —— Garmin 从 2026 年起暂停套餐仍保留 12 个月免费 SOS，Apple 卫星 SOS 随新机送多年。**我们把 SOS 做成需付费的功能，会在发布会当天被截图挂出来。**
2. **纯诊断工具订阅制挨骂，买断制活得好** —— Carly 年费被车主社区围攻，Torque/BimmerLink 买断口碑更好。订阅必须捆**持续交付的价值**（云端健康报告、二手检测、卫星流量），不能捆"解锁本来就在硬件里的能力"。
3. **国内 AI 育儿付费意愿弱、情绪陪伴反而卖得动** —— BubblePal 499 元送 3 年会员（之后 99 元/年，销量 25 万台）；芙崽半年 12 万台走的是潮玩情绪路线；牛听听 2025 年 9 月直接停会员内容全免费（收不上来）。
4. **模块化要学 M5Stack / CMF Phone，别学 Project Ara / Moto Mods** —— 核心机独立可用、接口对第三方开放、配件便宜热插拔；死于私有协议、模块定价高、SKU 碎片化。
5. **华为畅连北斗消息免费但限 16 次回复 / 60 秒间隔** —— 用硬限制控信道是行业做法。我们的流量包设计可以直接借这个形态。
6. **健康订阅不能单卖工具，要卖"有人管"** —— digivita 的闭环里真正付费的是"主理人审核 + 干预"这层人服务，工具本身留人。**健康助手在车宠里必须是 B+C 双收：用户订阅 + 健康顾问侧服务费**，否则又是一个收不上来的会员（牛听听前车之鉴）。边界见 §3.4：**督导服务，不是医疗服务**。
7. **结算主体用我们自己的**（你的评论已定：后续成立主体开展业务）。这意味着**不依赖吉利的渠道分成规则、不依赖时空道宇的计费口径**，卫星流量按"我们向时空道宇批发、零售给用户"的两段式做，价格与配额我们自主。⚠️ 代价也要写清：**自建主体意味着资质、发票、支付通道、退款与客服全部自己扛**，这是真实成本，不是"以后再说"。

收入结构（建议，非承诺）：

```
硬件   圆屏底座 + GT1005 终端 + 支架/线材        一次性毛利
订阅   守护会员（云健康报告 + 轨迹 + 家庭组）      年费，主力
健康   健康助手订阅 + 顾问服务费                  C 端订阅 + B 端分成，第二曲线（咨询非医疗）
流量   卫星消息条数包（含紧急 SOS 免费打底）        自有主体批发转零售，按条/按月
内容   亲子内容包（可选，第三方分成）              谨慎，验证过收不上来
```

## 10. 产品形态：App 还是小程序？

**结论：主产品必须是原生 App，小程序只能当引流和轻场景的补充，不能当载体。** 这不是偏好，是四条技术死线：

| # | 硬约束 | App | 微信小程序 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | **手机要当 WebSocket 服务端**（圆屏主动连手机，`:8443`） | ✅ 可以 | ❌ **做不到** | 小程序没有监听端口的能力，只能当客户端。现有架构（D8 决策）直接不成立 |
| 2 | **后台常驻与哨兵模式**（围栏越界、遗留车内、断链补发） | ✅ 前台服务 + 精确闹钟 | ⚠️ 只有极短的后台窗口 | 小程序切走就挂起，**"你没看手机时它替你看"这条产品主张直接归零** |
| 3 | **持续后台定位**（轨迹、寻车、模块 GNSS 融合） | ✅ | ❌ 后台定位受严格限制 + 需资质 | 这是车载/亲子场景的地基 |
| 4 | **BLE 连 GT1005、串口/USB 连 TTL** | ✅ | ⚠️ 小程序 BLE 只支持 BLE 4.0，无 USB/串口路径 | `UartModem` 这条在小程序里没有实现位置 |
| 5 | SOS 的可靠性与免责 | 系统级权限、可拨号、可紧急联络人 | 依赖小程序存活 | **在生死功能上依赖一个会被随时回收的容器，是我们不能签的** |

再看非技术面：

- **推送**：小程序只有"订阅消息"，一次订阅一次下发，且不能自主决定时机。SOS 回执、下次过顶提醒、围栏告警都要即时性 —— 全得自建 App 推送通道，本来就是这个产品的日常。
- **审核与内容**：亲子 + AI 对话 + 位置数据在小程序里属于强监管类目，被卡的是**上线节奏**，而且我们改不了审核口径。
- **付费**：小程序内购受平台规则约束（尤其虚拟内容/会员），而我们要卖的是硬件 + 卫星流量包，**走 App + 自有支付/线下渠道更干净**。
- **App 的代价**：装机、授权、更新。这是真实成本，别当没有 —— 尤其 P3 画像（老人带孩子）根本装不利索。

所以推荐的形态是：

```
原生 App（主力，安卓先行）  —— 链路、设备、后台、SOS、订阅
        +
小程序/快应用（引流与轻场景）—— 试驾预约、门店看车、家人只读共享卡、活动页
        +
圆屏展示端                  —— 车里的"常驻第二屏"，不承载账号与设置
```

**小程序唯一值得优先做的理由**是"家人共享只读视图"：爷爷奶奶想看孩子今天几点到的、走了多少步，让他们装 App 不现实。这类只读分享用小程序承接是最优解，且它不需要上面任何一条硬能力。

### 10.1 形态归属已定：独立 App + 自有账号，吉利是渠道之一

你评论里那条"吉利只是我们用户的一个部分，不能完全依赖这个渠道，我们要有独立的用户和产品策略"，**这不是偏好问题，是把产品主权写死**。原 V1.1 里我把"吉利是否要求做成其超级 App 内置小程序"列为 P0 待问 —— **本轮不再问，直接按决策落地**：

| 维度 | 决策 | 为什么必须这样 |
| --- | --- | --- |
| **载体** | **独立上架的原生 Android App**，不进入任何人的超级 App 内置 | 一进入内置，我们的上线节奏、推送权限、后台常驻、灰度能力全部变成别人的排期。上面那五条硬约束，一条都绕不过去 |
| **账号** | **车宠自建账号体系**（手机号 + 设备绑定 + 家庭组），不依赖吉利/亿咖通账号 | 硬件在我们手里、卫星卡在我们手里、订阅在我们手里。**账号在谁手里，用户就是谁的**。digivita 后续通过 `externalAccountId` 打通（§12 #6），不做二次注册 |
| **支付** | **自有主体收订阅费与流量包**（主体后续成立，§7 第 7 条） | 走吉利渠道分成，硬件+流量的毛利会被渠道费吃掉，且我们无法自主定价做促销 |
| **分发** | 吉利/4S 店/车机扫码 = **渠道之一**（还有硬件自带二维码、卫星套餐绑定、线上自营） | 吉利的车主流量确实值钱，**但要用"渠道合作"的方式拿，不是用"变成它的子模块"的方式拿** |
| **车机/亿咖通生态** | 做**投屏式对接**（圆屏或车机作为我们 App 的第二屏，走局域网 WebSocket），不做深度内置 | 深度内置 = 跟车机固件版本绑定，我们的迭代速度会被车机 OTA 节奏拖死 |

**代价也要说清楚，别只听好话**：独立 App 意味着**冷启动装机靠我们自己**。吉利渠道不给我们导流入口的话，用户获取只能挂在硬件销售上（买硬件才装 App），这会压低激活率；同时账号、支付、客服、退款、发票全部自建（§7 第 7 条已列）。**这两笔成本是"主权"的票价，我认为该付。**

**对吉利合作姿态的一句话表述（对外可以直接用）**：我们提供的是**车载场景的卫星守护与亲子陪伴能力**，吉利的车机可以成为它的展示终端之一；**我们不做吉利 App 的一个页面**。

### A.0 小智（xiaozhi-esp32）到底是什么，我们是不是必须要它

> 这条是对你 #4 评论的正式回答。**你评论里的前提是"链接写了支持小智那就一定支持"——前半句我同意，后半句（我们一定需要它）不成立，得纠正。**

**一句话通俗版**：小智是国外一位开发者（虾哥）开源的**AI 语音对话玩具方案**，GitHub 上 3.2 万星。它把"一块便宜的 WiFi 开发板 + 麦克风 + 喇叭"变成"能听懂你说话、会开口回答、能被随时打断"的东西。分成两半：

| 半边 | 是什么 | 我们如果自己做要花多少 |
| --- | --- | --- |
| **设备端固件**（`xiaozhi-esp32`，MIT） | 唤醒词检测、录音、Opus 音频流、播放、打断、多种板型的硬件适配 | 唤醒/降噪这一层我们用乐鑫 `esp-sr`（也是免费），但**打断时机、缓冲切换、AEC 调参**这套是几百小时调坑 |
| **服务端**（`xiaozhi-esp32-server`，MIT，1.1 万星） | 接 ASR（火山 / FunASR）、接大模型、接 TTS（CosyVoice / EdgeTTS），管会话与音色 | 这层我们**反正要自己建**（§3.3 的 AI 网关），因为我们要控制儿童内容过滤、要接自己的 Skill 注册表 |

**所以小智对我们的真实价值，只有一件事**：它证明了**这块板子的音频硬件链路是被别人趟过的**。商品页写"支持小智"，意思是双麦阵列 + ES7210 回声消除 + ES8311 编解码这套模拟前端，官方固件里已经有时序、有引脚定义、有已知可用的调参。**我们要语音功能时，可以从"硬件能不能出声"这个坑直接跳到"内容好不好"这个坑。** 这是省工期，不是产品能力。

**"一定需要"为什么不成立**——按场景拆开看：

| 我们的场景 | 需要小智吗 | 理由 |
| --- | --- | --- |
| §3.2 卫星守护（SOS、位置、消息队列） | ❌ **一行代码都不要** | 展示端在这只是"状态屏"：显示链路、剩余条数、位置。没有语音需求 |
| §3.1 用车养车（车况、保养提醒） | ❌ | 同上，读数据 + 画图 |
| §3.4 健康助手 | ❌ | 主战场在手机，打卡/图文/静默督导，语音是锦上添花 |
| §3.3 亲子陪伴（讲故事、问答） | ✅ **只有这一个** | 小孩不打字，孩子的交互界面就是一块会说话的屏 |

**正确定位：可选加速器，不是底座。** 架构上不能出现"因为用小智所以……"这种因果 —— 我们的五层架构（§3）里，语音只是 L4 呈现与形态层的一个输入输出通道，和触摸、通知同级。**反过来说：如果 1.75 移植小智踩坑，我们的应对是"亲子语音先用手机 App 承接，圆屏只做显示"，产品照常成立，只是亲子体验降一档。**

**那条真正的风险（§9 #7）**：小智官方**设备支持列表里没有 1.75**（只列了微雪 AMOLED-**1.8** 圆屏）。这不是"商品页骗人"——1.8 和 1.75 是同一家板厂、同一套音频前端，**差异在显示屏驱动（CO5300 QSPI 时序）和触摸（CST9217 坐标）**。所以移植是"改显示与触摸的两个驱动文件"级别的活，不是"从零做语音"级别的活。明天到货后的验证顺序：

1. 先刷官方现成固件，确认**能出声、能唤醒、能听到我说话**（音频链路，这是商品页承诺的部分）。
2. 再确认小智的**显示分支**能不能在 466×466 上点亮（这里最可能出问题，出问题也不影响第 1 步结论）。
3. 如果第 2 步炸了，我们的路径是自己写 LVGL 显示 + 复用它的语音（`esp-brookesia` 那套也在这条路上），**不要为了一个圆屏头像去改 QSPI 时序**。

| 量 | 数 | 说明 |
| --- | --- | --- |
| 物理像素 | 466×466 | 圆形区域占外接方框 **78.5%** |
| 逻辑分辨率 | **≈233×233** | 约 376 PPI，必须开 LVGL 2× scale，否则 12px 字糊成一团 |
| 最大内接方形内容区 | ~330×330 物理（≈165×165 逻辑） | 放文本/表格的硬上限 |
| 实际可用内容区 | **~290 物理** | 再让出 15–20px 边缘带做触摸手势，边缘误触率很高 |
| 圆形遮罩做法 | `radius=CIRCLE` + `clip_corner` | LVGL 9 原生，模拟器 / SquareLine / EEZ 都有圆屏选项 |

**结论：一块"看起来很大"的圆屏，能安全放字的地方只有约 165×165 逻辑像素 —— 大约 4 行 14px 中文。** 所以 §4 的呈现层规则必须是**一屏一主信息 + 一个动作**，凡是"卡片里再套三行说明"的设计在这块屏上都是废的。这也解释了为什么 `StatePayload` 要按"字段 + 优先级"下发，而不是让展示端自己排版。

### A.4 与本项目现有设计的四条硬对应（**不是建议，是缺口**）

1. **`dock_type` 是错的抽象。** ESP32 侧没有 device tree，`dock_type` 只能靠 ADC 分压电阻或 1-Wire 芯片识别。行业做法是**按「面板几何 + 可用输入设备 + 朝向」三参数自适应**（Brookesia 就是这么分层应用的）。这恰好是 `screen-link` hello 里缺的字段 —— 现有 `avatar_mode` / `dock_type` 不解决布局问题。**建议 hello 增补 `screen: {w, h, round, touch, ppi}`。**
2. **屏有触摸，§4 的输入模型要改。** 之前按"无触控、靠底座按键"设计的卡片路由作废：主输入是触摸（点按 + 边缘手势），底座按键退化成 SOS 硬键和"上一屏/下一屏"两个键。⚠️ 466² 圆屏的**触摸目标不能小于 8–9mm**，车载颠簸场景还要再放大。
3. **语音链路已经现成，端到端延迟才是问题。** 小智路线：Opus 16k 流式上行，ASR 可选火山 / FunASR-SenseVoice（GPU 上 10s 音频约 70ms），TTS 可选 CosyVoice / 火山 / EdgeTTS，**端到端体感 1–2s**。所以 §3.3 亲子场景的技术风险不在"能不能做"，在**离线/蜂窝断链时的降级体验** —— 卫星链路绝对撑不住语音，必须明确"没网就不聊"的 UI 说法。
4. **协议方向要择一。** ESP-Brocast 走 UDP 多流音频、`esp_event_network_examples` 走 SoftAP + Web，我们现在走 **WebSocket 文本 JSON**。三种都能配网，但**并存等于三份心跳和三套重连**。建议：控制面保留 WebSocket JSON，音频面另开一条 UDP（小智本来就是 Opus over WebSocket/UDP，可对齐）。

### A.7 五条必须避开的坑

1. **`dock_type` / `avatar_mode` 没有上游可抄。** 「BLE/Wi-Fi 圆屏 ⇄ 手机自建服务」这个精确组合在 GitHub 上零结果（`M5Stack`+`Android`+`BLE`、`watchface`+`phone companion` 都搜不到）。唯一性归我们，**文档漂移的风险也全归我们** —— 这也是 DECISIONS.md 里契约版本要写死的原因。**北斗/GNSS 短报文 + ESP32 + Android 端 App 同样没查到可借鉴的开源实现**（meshtastic 是 LoRa 网状网，射频模型可看但报文口径完全不同）。
2. **LVGL 8.x → 9.x 迁移是隐性成本。** WT-OBD 及多数 2024 年前的项目在 8.3，`lv_arc` 与显示旋转 API 有 breaking change，抄代码前先对齐版本（**我们的下限定 LVGL 9.5**）。
3. **别为图形界面引入第二套 RTOS。** ESP-IDF + LVGL 9.5 在 S3 上已经够；RT-Thread 的 GPU/显示例程停在 LVGL 7.4，从那儿起步等于先还一笔债。
4. **别把微雪另外两块圆屏的例程当同一份。** 1.46 寸 T-UI 那块是**双芯片驱动**（GC9503NP3 应用 + AXS15231B 触摸）；还有一块 1.46 是 GC9A01 SPI。我们的 1.75 是 **CO5300 QSPI + CST9217**，**init 序列不能照抄**，只能用同一仓库里 1.75 自己的例程。
5. **本轮调研出现过自相矛盾**（一次说微雪例程可直接照抄，一次说找不到任何可引用的圆屏 LVGL 例程）。我用直接访问仓库的方式做了裁定（见 A.3 第一行的核实结果）。**教训：涉及具体仓库路径的判断，以直接核实为准，不要采信二手摘要。**

### A.8 建议抄的三件事

1. **先把微雪官方例程 `examples/02_lvgl_demo_v9` 和 `03_esp-brookesia` 跑起来**（同板、同驱动、同触摸，工具链按 ESP-IDF v5.5.5 或 v6.0.2），再谈我们自己的卡片层 —— 这一条能把展示端固件的工作量砍掉一半。
2. **语音不自研链路**：走小智（`xiaozhi-esp32` + 自建 server），端侧只用 esp-sr 做唤醒词和少量离线命令；**1.75 未在官方支持列表里，移植预算按"屏+触摸适配"估，不要按"语音适配"估**。
3. **抄 `esp_event_network_examples` 的 SoftAP 配网状态机**：STA 连不上自动起 SoftAP + 内置 Web 配网页，配完自动关 —— 现场没有可用 Wi-Fi 时这就是救场路径。

### B.3 车载业务参照

- **AndrOBD**（`fr3ts0n/AndrOBD`，约 2.2k⭐）：**GPL-3.0 —— 不能抄代码进闭源 App，只抄信息架构**：PID 分组、实时读数仪表、DTC 读取与清除、日志导出。§3.1 的故障码模块照它的 IA 设计。

- AARE（`prototux/AARE`，Android Auto 手机侧重实现）：概念验证，参考价值低。

### B.4 亲子业务与合规

- **KidSafe**（`xMansour/KidSafe`，MIT）：应用屏蔽、时长管控、定位的家长端 IA，**可复用代码**，对应 §3.3 家长管控 P0。

### D.3 digivita 的坑，我们必须写进交付判据

1. **后端稳定性欠债**：1.8G 内存无 swap，**PM2 重启 4624 次**，`journalctl` OOM 杀进程（`BACKEND_ISSUES_REPORT.md:288`）。→ R1 判据要含内存基线与部署自动化。
2. **无测试、无 CI/CD、手动 SSH 部署**，且交接文档自己写明 706 个 TSX 只有一个测试文件（`PROJECT_HANDOFF.md:423`）。→ 我们现在有 43 条 core 单测，**这是不能倒退的底线**。
3. **首屏全量加载（懒加载没做）**、GSAP 与 Framer Motion **两套动画库重叠** —— 交接文档把动画库列为最高优先级待办。→ §5.2「简约精美」的反面教材：**动画库只留一套**。
4. **大量返工记录**（`*FIX*.md`：打卡、热量、数据同步、底部导航、滚动、路由），说明**数据模型与导航结构早期没定死**。→ 这就是 §5.3 要把 `SceneProfile` 写进契约的理由。
5. **明确写了「不做」的**：不给 AI 无限制 Shell（"DigiVita 不需要，避免引入"）、未审批不执行破坏操作、不存明文凭据、不信未验证 Skill、**不靠提示工程防注入**；医疗安全上**不自动开药、不诊断、不做医学判断**，只给生活方式干预。→ 全部照抄进 §3.4 红线与 §L2 AI 网关。
6. **Skill 生态选型踩过的雷**：只查询不分析的（Food DB、Medical Records Query）不要用；默认中文能力缺失的（食物库/体检标准/代餐配方）不要直接用；**未验证 Skill 自动进系统 = 安全隐患**。→ 接第三方能力用同一把尺子。
7. **合规与商业底线**：医疗建议必须有专业审核签字、**用户健康数据绝不外传**（合作底线是"数据留平台、背书边界清晰、首次不谈股权"）。→ §6 与 §11 的主理人条款按这个口径写。
8. **多端一致性是隐性成本**：同一套健康功能维护 **Flutter App + 微信小程序 + Web + Python 后端** 四端，Flutter 侧还出现"后端实现了 9 个接口、前端只接了 1 个"（`app/backend/OPENCLAW_ANALYSIS_FOR_DIGIVITA.md:765-777`）。→ **§10 要求设备契约单一权威，否则每加一端都要重连一次。**

### D.4 对我们最有价值的一条反面证据：**他们的小程序 = WebView 嵌 Web + 原生蓝牙 Tab**

`docs/小程序.md` 与 `PROJECT_HANDOFF.md:454` 记录的形态就是这样：**唯一必须走原生桥的恰好是设备同步（小程序做不了那件事）**，其余全是 H5；另外还有一份 `Flutter迁移方案.md` 在评估把混合栈整体迁走，`CLAUDE.md:114-121` 写清了"先 Web 验证，再迁 Flutter 与小程序"。

**这正是 §10 结论的实测版**：小程序容器承载不了硬件能力，最后必然长成"原生补丁 + WebView"的杂交体，然后被迫二次迁移。车宠的设备比一个戒指多得多（卫星终端 + 圆屏 + 车辆 + 戒指），**没有理由重走这条路**。

### D.5 还缺的（别以为 digivita 全都给了）

- **没有可穿戴实时异常告警**：告警只有打卡提醒/里程碑/周报/教练提醒，**没有心率异常这类实时告警**（`alert/` 模块可证）。→ 车宠要做的"心率异常 × 疲劳驾驶"是**新增能力，含车规安全责任**，别当成改改就能用。
- **体脂秤、语音记录只停在设计稿**，没实现。
- **没有选品/商城的落地实现**，`大橙拾光站 公益玩法设计.docx:160-203` 只有设计层描述 → 别当现成商业模块。
- **家庭/代管视角很薄**（只有积分转赠、社群分组、报告分享）→ 亲子场景的"家长看孩子"要自己设计。

### D.6 一句话总结

**真正能搬的就三样：双角色打卡闭环、Skill 三层 + Heartbeat 主动机制、健康主理人角色。** 其余都要重做或新增 —— 尤其**实时异常告警**和**硬件接入契约**这两块，恰好是车宠的强项，而 digivita 的 `docs/接口文档.md` 只写了设备同步接口、没有"设备能力契约"这一层。

### E.1 最重要的一条：SDK 不做 IO，传输层归我们

SDK 只暴露一个回调接口让我们实现，它自己不碰蓝牙也不碰串口：

```java
DispatchManager dm = new DispatchManager(new ModuleOperation() {
    void initialization(boolean isReady);   // SDK 是否可用；未就绪时任务返回 INITIALIZE_ERROR
    void passthrough(String pactWrap);      // 所有收到的标准语句原文，方便应用自行解析
    void send(byte[] data);                 // ★ SDK 要发的字节，由我们送到模组
    void powerOn(); void powerDown();       // 模组上下电，由我们实现
});
dm.receive(byte[] data);   // ★ 模组吐出来的字节，由我们灌给 SDK
dm.start();                // 开启循环解析
ModuleDataManager m = dm.getDataManager();
```

〔码〕`DispatchCallBack` 里就是 `send([B)V / powerOn / powerDown`；〔码〕参考实现 `CommunicationManager.send()` 转调 `BleManager.getInstance().sendData(data)`；〔码〕`MainFragment` 里 BLE 状态到 `LINKED` 才 `dispatchManager.start()`。

**这条决定了三件事：**

1. **我们的 `UartModem` 路线合法，不用推翻。** 〔规 §2.1.1〕UART 是标准物理承载：波特率 **9600 / 38400 / 115200，默认 115200**，数据位 8、停止位 1、无校验；芯片或模组集成形态可映射为片上 UART / 虚拟串口 / 主控接口。官方 demo 走 BLE 只是**它的一种实现**，不是唯一入口。
2. **`Gt1005Verbs` 那张手写指令表应该删掉，`UartModem` 退化成纯字节管道。** 语句组包、异或校验、字段解析全交给 SDK —— 自己实现一遍等于把厂商已经趟平的坑重新踩一次。
3. **`passthrough(String)` 是现场排障的救命稻草**：把每条原始语句打到工程模式日志窗，出问题一眼能分清是模组没回还是我们没发。

### E.2 协议形态：NMEA 风格 ASCII 语句，不是二进制

〔规 §2.2.1〕`$<5位类型标识>,<字段>,…,<字段>*<2位hex校验和><CR><LF>`。
**校验和 = `$` 与 `*` 之间全部字符按字节异或**，前 4 bit 与后 4 bit 的 hex 值分别用 ASCII（0-9、A-F）表示，高位优先传输。
〔规〕发射器标识：上位机发的用 `CC`（如 `$CCSFQ`），通信单元输出的用 `GS`（如 `$GSMCI`）。
〔规 §3.1.11/3.1.12〕**通信数据字段是十六进制的 ASCII 表示，不是原始字节**：例 `0x0102A1A2` → `$CCSFQ,0,0,0102A1A2*48`。〔码〕所以 `sendMsgSFQ(cardId, UsualUtils.byteArrayToHex(bytes), …)` 这层 hex 转换是强制的。

> **§9 #1 里"ICI 是二进制还是 hex"这半个问题，规范已经答了：整条协议是 ASCII 语句，数据字段是 hex-of-bytes。这半条不用再问厂商。**
> 推论：**业务消息必须自带一层序列化格式**（我们自己的 TLV 或紧凑 JSON），因为协议只搬字节。90B 预算下，JSON 的引号和字段名都是奢侈品——这直接决定 §3.2 的报文编码设计。

### E.4 ICI 字段 9：消息长度是**分等级**的（V2.0 那个"自相矛盾"其实是等级差）

〔规 §3.1.4 注 7〕「通信单元发送消息长度」定长数字 **1~5**：

| 等级 | 上限 |
| --- | --- |
| 1 | **≤90 B** |
| 2 | ≤200 B |
| 3 | ≤230 B |
| 4 | ≤430 B |
| 5 | **≤1900 B** |

> **这解决了 V2.0 方案文档里"单包 ≤1900B"（61 行）和"ICI ≤90B"（595 行）互相打架的问题：两个都对，取决于这张卡/这颗模组被开成哪个等级。**
> **架构结论：运行时读 ICI 再决定报文预算，绝对不许把 90 或 1900 写成常量。SOS 报文骨架按等级 1（90B）设计才安全，其他等级只放宽不收紧。**

〔规 §3.1.4〕ICI 其余字段直接划定产品能力边界，一个都不能忽略：

| 字段 | 含义 | 对我们的影响 |
| --- | --- | --- |
| 1 卫星号码 | 变长字符；**`1` 为无效卡** | 检测到无效卡时**通信单元不进行选星**。App 必须把"卡无效"和"无信号"分成两种 UI，不能都显示"搜索中" |
| 2 链路模式 | 固定 1：DCS-D | — |
| 3 组网方式（bitmask） | Bit0 通信单元-平台 | 只有单元-平台权限时**只能跟平台收发**，点对点分发要另开权限 |
| 4 服务类型 | **1 长接入 / 2 短接入** | **收信状态机按这个分叉**：长接入自动收下行的 MCI；短接入必须主动发 CEQ 查询 |
| 6 通信方式（bitmask） | Bit0 实时回传 / Bit1 存储回传 / Bit2 实时分发 / Bit3 存储分发 | **只有"实时回传"权限的模组只会选具备地球站跟踪或星间链路的卫星** —— "能不能马上发出去"是权限问题，不是信号问题 |
| 8 卫星应答模式 | 0 无应答 / 1 有应答 | 无此权限时**所有消息卫星都不回 ACK**，SOS 上"已送达"的文案在这张卡上是假的 |

〔规 注 6〕**"卫星应答只是表示卫星收到该消息，并不代表星座核心网收到。"**

### E.5 TPI：手机的位置是要**喂给模组**的，不是从模组读出来的

〔规 §3.1.7〕TPI 输入 UNIX 秒 + **度分格式**经纬度：纬度 `ddmm.mmmm` + N/S，经度 `dddmm.mmmm` + E/W，**前导 0 也要传输**。
〔规 注〕**通信单元上电必须配置一次，后续建议 1~10 分钟更新一次；模组复位、掉电后时间位置信息丢失。时间信息对上下行无影响，经纬度对下行接收有影响。**
〔规 注 1〕时间字段为 `0` 时，表示模组内部已有的经纬度数据**无效**。
〔码〕`ModuleDataManager.updateLocation(double longitude, double latitude)`，且 **SDK 自己保存最近一次经纬度、模组每次启动自动补发**，所以"至少更新一次"由 SDK 兜底，但仍要我们按 1~10 分钟续。
> ⚠️ **V1.4 实测补两条（E.12），这两条把"TPI 是不是真的喂进去了"变成不可观测：**
> ① `updateLocation` 的返回类型是 **`void`**，不是布尔、不是任务对象 —— SDK 层面**没有"模组认了这条 TPI"的回调**。aar 里确实有 `bean.EntityTPI`（带 lat/lon/direction），但 `ModuleDataManager` 的六个监听器里**没有 TPI 那一个**，`Parse` 包也没有对外暴露 TPI 回显的入口。所以我们代码里 `updateLocation(): Boolean` 的 `true` **只表示"一个字节都没被升级写锁挡住、已经交给 SDK"**，绝不表示模组内部位置已更新（§9 #17）。
> ② **`EntityDII` 压根没有位置字段** —— 实测只有 `DTU_Type / Module_SoftwareVersion / Module_HardwareVersion / DeviceSerialNumber / UserVersion` 五个 getter。配合〔规 §3.1.2 注〕「DII 里的时间和经纬度均由外部通过 TPI 输入」，**"从模组读位置"这条路在 SDK 面上是不存在的**：要么这颗模组自带 GNSS（文档没说，§11 要问），要么读回来的是我们自己几天前推进去的回显。所以代码里 SDK 路线的 `readFix()` **直接返回 null 而不是编一个值**，车内/屏蔽袋场景的位置源只有手机自己这一条（§3.2 定位融合不是可选增强，是唯一路径）。

> **这条改写 §2 的定位融合方向**：手机 GPS 是模组的**必要输入**，不是可选增强。
> 于是"地库里没定位"要重述为：**用的是最后一次成功 TPI 的位置**，而不是"完全没位置"。寻车、遗留车内告警、围栏都因此更可用；但代价是 **TPI 陈旧度必须成为一个可观测状态**上屏 ——「位置已过期 N 分钟，卫星可能投递失败」，这是新加的 §4 呈现字段。
> 另外 SDK 的 `updateLocation` 参数顺序是 **(经度, 纬度)**，而 TPI 语句是**纬度在前** —— 这种顺序陷阱一定会在联调时咬人，代码里禁止用裸 double 传坐标，一律走 `MyLocation`/带名字的类型。

### E.6 队列与超时：GM1001 和 GM1003 是两种完全不同的东西

〔规 §3.1.12 注 / §4.1〕

| | **GM1001** | **GM1003** |
| --- | --- | --- |
| SFQ 存储介质 | 内部 **FLASH，掉电不丢失** | 内部 **RAM，掉电丢失** |
| 最大存储条数 | **500 条** | **50 条** |
| 优先级字段 | **不支持，固定填 0** | 支持 0~2，**数字越大优先级越高** |
| 超时机制 | **无超时机制** | **默认超过 4 分钟未发出即主动丢弃**，SFI 回"报文发射失败 / 超时" |

〔规 §3.1.13〕SFI 报文状态 `1~4`：**1 已存储 / 2 完成该报文发送 / 3 存储失败 / 4 发射失败**；失败原因 `1~3`：**1 数据长度超过最大限度 / 2 缓存区已满 / 3 超时**（仅状态 3 生效）；**报文 ID 由通信单元生成，1~65535 循环，存储失败时该字段为 0**。
〔码〕参考 demo 判成功用的是 `entitySFI.getState() == 2`。

> **本轮最要命的发现：我们的采购与方案口径一直写 GT1005，但规范里只有 GM1001 / GM1003 两颗模组，而它们在"掉电保不保、能存 500 还是 50 条、SOS 会不会被 4 分钟超时丢掉"上完全不同。**
> **§9 #1 因此升级为 P0 的第一问：GT1005 对应哪一颗？** 如果是 GM1003，那 §3.2「存发队列 + 断链补发」这条产品主张的物理上限只有 **50 条、掉电即清、4 分钟不发就丢** —— 队列设计要整个重做（App 侧自建持久队列兜底，而不是依赖模组），"补发数量上屏"这个演示点也得改口径。

〔码〕SDK 已经把这条链给全了：`clearSFQ()` / `queryMsgSFQ(Consumer<Integer>)`（返回 `<0` 表示查询失败）/ `sendMsgSFQ` 成功回调的 `bundle` 就是报文 ID，可直接与 `setSFIMessageListening` 对上。**补发状态追踪不用自己造轮子。**
> **V1.4 实测更正（E.12）：`sendMsgSFQ` / `sendMsgMCQ` / `queryMsgSFQ` / `updateSOC` 的返回类型不是 `void`，而是 `com.geesatcom.wheel.SubjectTask<*>`。** 这既是好事也是坑：好事是**超时可以自己兜**（我们给发送另设一个计时器，到点 `task.cancel(null)`，别让 SOS 卡在一个永不回调的任务上）；坑是**任务对象是 SDK 的内部调度单元，取消语义没有文档**（`cancel(Object)` 的参数该传什么、取消后回调还来不来、会不会回 `CustomError.REMOVE`），所以代码里取消只用在"我们已经等到超时"这一种情况，并且**把超时结果归到 `NO_REPLY`（没发出去）而不是 `DROPPED_BY_TIMEOUT`（发出去被丢）** —— 后者的重试策略是把同一条再排一次队，前者不能这么干。**"已存储(1) → 完成发送(2)" 的中间态回调，SDK 只在 `FAIL` 分支写了文档，`state==1` 会不会推给我们，必须真机验证**（§8 R0 → R1 的第一次真机联调）。
〔规 §3.1.14〕SFP 示例：查询待发数量 `$CCSFP,2,1,,*46`；清除所有待发 `$CCSFP,1,2,,*46`。

### E.7 MCQ 的 `NO_ACK`：SOS 的"半成功"态，产品必须显式建态

〔SDK文 §4.1〕`CustomError` 只有四个值：`INITIALIZE_ERROR`（SDK 未可用或模组正在升级）/ `INPUT_ERROR`（参数不正确）/ `REMOVE`（任务被移除、重复调用）/ **`NO_ACK`**。
> ⚠️ **V1.4 实测更正（E.12）：aar 里 `CustomError` 是五个值**，文档漏了一个 **`TIMEOUT_ERROR`**。这一个值直接决定"发出去没人认"和"等太久没回"要不要分开显示，代码里按五个建全。**另外 `TaskState` 实测是 `{INIT, START, COMPLETE, FAIL}` 四态**，`INIT/START` 是进度态不是终局 —— 我们的三态只认后两个，`INIT` 阶段就回来的一条不能当失败（否则 SOS 会被自己骗一次）。
〔SDK文 §8.3〕MCQ 即时发送：`FAIL` 时 `bundle` 是 `CustomError` 或模组返回码（**参考文档 FBI 定义**）；**`COMPLETE` 且 `bundle == CustomError.NO_ACK` 表示"发送完成，但未收到 ACK"**。〔码〕`SubjectTask.cancel(Object)` 可取消发送。

> **`NO_ACK` 既不是成功也不是失败，这恰好是 SOS 最真实的那个状态。** §3.2 的"无 ACK 自动重发"必须把它建成独立态（文案：「卫星已收下，但未确认回执」并给出重试），否则要么骗用户，要么把已经成功的报文重复发一遍占配额。

〔SDK文 §8.2〕SFQ 的 `FAIL.bundle` 若是 Integer → 参考 **SFI 定义**；MCQ → 参考 **FBI 定义**。〔码〕`ParseFBIS / EntityFBSI(utc, success, code, frameNum)` 确实存在，**但规范正文没有 FBI/FBIS 的字段表** —— 要问（E.11 #2）。

### E.8 线程模型：两个 SDK **完全相反**，这是集成期最容易炸的地方

| | 基础通信 SDK | 星历 SDK |
| --- | --- | --- |
| 调用线程 | 未见强制 |〔SDK文 §6〕**所有函数调用需在主线程执行** |
| 回调线程 |〔SDK文 §9〕**所有回调均在子线程**，需自行切主线程 |〔SDK文 §6〕**所有回调在主线程执行**，内部自行切换不阻塞 |
| minSdk | **24** | **26** |
| JVM Target | 11 | 11 |
| 依赖 |〔SDK文 §3〕aar 放 `app/libs` + **RxJava3 3.1.12** | aar 放 `app/libs` |
| 额外要求 | — |〔SDK文 §3.2〕Manifest 需 **`usesCleartextTraffic="true"`**（明文下载星历轨道数据）；〔SDK文 §8〕**必须普通应用签名，使用 Platform Signature 可能导致 SDK 无法运行** |

〔SDK文 §9-2〕**"如果当前正在更新模组任务，所有数据发送和自定义任务都不可用。"** → 升级期间要**全局写锁**，§5.2 的按钮禁用态必须覆盖这一档；〔SDK文 §8.1〕`updateSOC` 进度 0~99 已给，失败码分 `CustomError` 与模组整型码两类。

> **V1.4 实测加三条（E.12），都是集成期会直接炸人的：**
> ① **依赖不止 RxJava3 一套生态**：`ModuleDataManager` 的六个监听器**入参是 `java.util.function.Consumer<T>`（JDK8 API），返回值却是 `io.reactivex.rxjava3.disposables.Disposable`**。于是 minSdk 24 那个下限是被 `java.util.function` 卡的、RxJava3 是被 `Disposable` 卡的，两件事来源不同。工程后果：**Kotlin 侧不能把一个函数值当 Java Consumer 传**（Kotlin 只对 lambda 字面量做 SAM 转换，对已经存成变量的 `(T)->Unit` 不转），适配器签名必须直接收 `Consumer<T>`。这一条我们踩了一次才编过。
> ② **`ModuleDataManager` 的构造函数是包私有**（`ModuleDataManager(ModuleOperation, android.os.Looper)`），应用代码 new 不出来，**只能从 `DispatchManager.getDataManager()` 拿** —— 意味着"SDK 没起来就返回 null"是必须处理的路径，不能当异常忽略。
> ③ **资料包里的 `jar_comm.jar` 和 `protocollibrary_1.0.0.aar` 是两个不同构建**：`DispatchManager` 在 jar 里有 `destroy()`，**aar 里没有**，只剩 `stop()`。所以按文档写的释放顺序在 aar 上根本编不过（我们实测报错）。当前代码 `close()` 只做"解订阅 + `stop()`"，**`stop()` 之后模组侧的解析线程到底停没停、要不要额外 `powerDown()`，得真机验证**（§9 #18）。
> ④ **星历 aar 里带 `libdecodeutil.so` 且部分类是混淆过的**，所以它抛的不一定是 `Exception`：缺 so / 缺系统 WebView 时是 `UnsatisfiedLinkError`、`NoClassDefFoundError`。彩排现场一次崩溃比一次算不出星历难看得多，因此适配器在这个插件边界上**捕获 `Throwable` 并降级成"星历暂时算不出来"**（E.9 的文案分支），而不是让它穿透到 Activity。

> **minSdk 取 26**（被星历 SDK 卡住），要回记到 §11 的前置条件里，这直接影响机型覆盖和吉利车主的旧机比例。
> **`usesCleartextTraffic=true` 是安全债**：为了星历下载给整个 App 放开明文不合理。工程上要么单独隔离这条下载（独立进程/独立域名白名单），要么推厂商上 HTTPS；无论哪种，**§6 要记一笔**。
> **"不能用系统签名"对我们尤其关键**：将来若走吉利前装、要求 platform 签名，**星历 SDK 可能直接跑不起来**。这是 §10.1「车机只做投屏式对接、不做深度内置」的一个新增硬理由。

### E.9 星历能力（我们一直想做的"下次过顶"，厂商已经给现成的了）

〔SDK文 §4〕`StarManagerFactory.getStarManager(context, Consumer<Long> dataState)`，回调 `-1` 正在通过网络下载 / `0` 下载失败且本地无可用缓存 / `>0` 当前使用的星历数据时间戳。
〔SDK文 §5.1〕`StarManager.calculate(RequestBean, ResultCallBack)`；`RequestBean = {lon, lat, alt(米), Elevation(可选，默认 20°，最高 80°), hour(小时)}`。
〔SDK文 §5.1.3〕`CalculateResultBean = {starName(对外展示名), startTime(入境), endTime(出境), startAzimuth(正北 0° 顺时针 360°), endAzimuth, maxElevation}`，结果按开始时间戳排序。
〔SDK文 §5.1.2〕`resultState`：`SUCCESS / NETWORK_ERROR（无星历数据且无缓存）/ TIME_OUT / CALCULATION_FAILED`；非 SUCCESS 时 `result` 为 null。
〔SDK文 §5.2 / §8〕建议**每日在有网时 `update()`**；**位置变化超过 20 公里要主动重算**；不用时 `release()`。
> **V1.4 实测补三条（E.12）：**
> ① `RequestBean` 有两个构造：`(double lon, double lat, double alt, int elevation, int hour)` 和 `(double, double, double, double, int)` —— **`hour` 实测是 `int`**，文档写"小时"容易让人传 0.5 天这种数，代码里按 `horizonHours.toInt().coerceAtLeast(1)` 收口，**宁可多看不如看不到**（0 小时会算出空窗口，跟"没有星"一模一样，是最难查的假故障）。
> ② **`update()` 返回 `void`**，下载成功与否只能从 `getStarManager` 的 `Consumer<Long> dataState` 回调里推（`-1` 下载中 / `0` 失败且无缓存 / `>0` 当前数据时间戳）。适配器因此必须**先记旧时间戳、再等一个"和旧值不同"的回调**，否则拿到的 `>0` 可能只是创建时就喂过一次的那条缓存时间戳 —— 会被误判成"刚下载成功"。
> ③ **主线程约束是真的**：适配器把 `getStarManager / calculate / update` 全部 hop 到 `Dispatchers.Main`（core 侧接口做成 `suspend`，`Looper` 一个字都不进 `:core`），这跟基础通信"回调全在子线程"正好相反（E.8）。彩排时最容易犯的错是"在协程里随手调"，一崩就是演示现场崩。

> 直接改写 §3.2「星历管理与失效提示」：`secondsToNextPass()` 这个抽象现在有真实现了，而且厂商给的是**过境窗口 + 进出方位角 + 最大仰角**，信息量远大于我们原来只算的"还有 N 秒"。
> **圆屏因此可以多演一个真有用的东西：野外时的方位角指针**（告诉用户"该把车头/天线朝哪边"）。这是这次 SDK 带来的净新增演示点。
> **`NETWORK_ERROR` 必须映射成明确文案**：「星历数据已过期，请联网更新后重试」，**不能显示"无卫星信号"** —— 这是我们原来会犯的错。
> 仰角阈值（默认 20°）要按我们终端的实际可通信仰角配，不能一路用默认值。

**这张表换来的三个设计决定**

1. **`VendorSdkModem` 不是 `SentenceModem` 的复制品**：两者实现同一个 `SatelliteModem` 接口、共用同一套语义（三态 / 写锁 / 预算 / 工程模式窗），所以 `DemoEngine` 一行没改。**SDK 路线仍然要走 `sendGMO(target, 2, 0/1)` 手动开语句**才能拿到 DII/ICI —— 因为 `ModuleDataManager` 只有 listener、没有"主动读一次并同步返回"的 API。**这正好独立证明了 E.10 #2（会话顺序）对两条实现都成立，不是我们臆造的时序。**
2. **SDK 路线上三处"没有数据"就是没有数据**：`readFix()` 返回 null（E.5 ②）、`secondsToNextPass()` 交给星历 SDK、`updateLocation()` 的 true 只到"已交给 SDK"（E.5 ①）。**编一个好看的值比承认不可观测更贵** —— 演示时骗过自己，联调时一定赔回去。
3. **这两类代码在 JVM 上测不了**：绑定 aar 类和 `android.util.Pair`，只能用"`:app:assembleDebug` 编得过 + aar 签名对得上"当编译门禁，行为一律留到真机（§8 R0 行那条 ⚠️：**仍未对真机发过一帧**）。**`:core` 那 158 条单测覆盖的是语义，不是厂商。**
