## 0. 一句话

**不是「猜你喜欢」，是「你的车现在这个样子，所以该做这几件事」。**

每一条建议都必须能回溯到 `(读数, 判据, 判据来源)` 这个三元组。回溯不了的，不许出现在界面上 ——
这条不是文案要求，是 §2 那个数据模型的要求：`Suggestion` 里没有那几个字段就编译不过。

---

## 1. 为什么不做成「推荐流」

三个理由，按重要性排：

1. **没有可推荐的东西。** 我们没有商品目录、没有门店、没有电商账号。一个推荐流界面在没有货的时候
   只能塞假货，而**假货比假数据显眼十倍** —— 假数据观众会当成演示，假货观众会当成我们能下单，
   然后现场问「那我点下去怎么买」，这一问就把整个 demo 打回原形。
2. **车况这个输入天生是规则的输入，不是偏好的输入。** 胎压 2.3 对标定 2.5 不需要模型。
   模型在这里唯一能出错的地方，是它替我们**编了一个判据** —— 而这套东西的可信度全押在判据上。
3. **品牌不对。** 这个 demo 从头到尾的说服力来自「每一句话都有出处」。

所以这一版做的是：**该做的事（动作）+ 一张能带走的工单**。
"商品"只出现在两个位置上，而且都是我们自己的东西（卫星额度包、车载应急包），见 §4 第 5、6 条。

## 2. 模型：四层，别糊成一层

```
Signal（读数）   →   Rule（判据）   →   Suggestion（建议）   →   Fulfilment（兑现）
胎压 2.3 bar        标定 2.5，低 0.2     「补气到 2.5」          勾选 → 进工单 → 发出去
```

```kotlin
// core/vehicle —— 新建。现在那四个数字是写在 SceneCards.kt 里的字符串，必须搬进来
data class Reading(
    val key: ReadingKey,          // tirePressureFl / odometerKm / rangeKm / avgEnergy / ...
    val value: Double,
    val unit: String,
    val source: Source,           // 见 §3
    val takenAt: Long,            // 墙钟。没有这个时间的读数不参与"趋势"类判据
)

data class Rule(
    val id: String,               // "tire.low"，工单编码里就是这个 id 的 1 字节码
    val needs: List<ReadingKey>,  // 缺任何一条读数 → 这条规则**不产生建议**，也不产生"数据不足"那行字
    val threshold: String,        // 人读的判据："标定 2.5 bar，低 0.2 以上"
    val thresholdSource: Source,  // 判据自己的来源，和读数的来源分开记
    val severity: Severity,       // due 到点 / soon 临期 / note 知会
    val window: Window?,          // 时限：里程差 or 天数
)

data class Suggestion(
    val rule: Rule,
    val evidence: List<Reading>,  // 界面上露出来的那几行读数。**空列表不允许存在**
    val headline: String,         // 「补气到 2.5 bar」
    val body: String,             // 一到两句，只说事实和下一步
    val fulfilments: List<Fulfilment>,
)
```

**界面上永远同时露出读数和判据两行**，一行数字、一行小字标出处。
这条决定了这一版和"AI 养车助手"那类东西的区别：它可核对。

## 3. 判据从哪来（这是最会被追问的一张表）

七档，UI 上直接印出来，不藏：

| source | 是什么 | 现在有没有 | 标在界面上 |
| --- | --- | --- | --- |
| `stub` | 我们自己编的演示值 —— **现在四个数全是这档** | 有 | `示意数据 · 未接真源` |
| `device` | 车上传感器直读：OBD 盒子、独立胎压传感器 | 待采购，见 `docs/VEHICLE-DATA.md` | 不打标 |
| `cloud` | 车厂车联网平台 —— 唯一能一次拿到续航/SOC/里程/胎压全项的路 | 只有吉利侧能开（◆4） | 不打标 |
| `nominal` | 标定值：B 柱标签上的标准胎压、手册上的额定载重 | 无真资料，先按示意 2.5 bar | `示意判据 · 未接手册` |
| `manual` | 保养手册的间隔：里程 / 月数，先到为准 | 无，等你给（§11 ◆1） | `示意判据 · 未接手册` |
| `kb` | **第二阶段**：车型养车知识 / 商品 / 门店知识库里的条目，带 `docId + version + clause` | 等你的资料，格式在 `VEHICLE-DATA.md` §5 | 「依据：银河 L7 保养手册 v3 §4.2」 |
| `observed` | 我们自己从数据流算出来的：能耗趋势、连续停放天数、里程增速 | 有，但喂的是桩读数 | `示意数据 · 未接真源` |
| `user` | 车主填的：上次保养里程/日期、车上有没有急救包、孩子身高年龄 | 这一版就做录入 | `你填的` |

**读数的来源和判据的来源是两条独立的轴**，各记各的档。
「OBD 读到的胎压（`device`）比对标定值（`nominal`）」这条建议里，一个是真的、一个还是示意的 ——
两个标都要露出来，不许因为读数变真了就顺手把判据那个标关掉。这是同一件事的两个半，
假装它们一起变真是在说谎。

**「示意数据」那个标必须由 `source` 驱动，不许由 `demo_mode` 驱动。**
挂在 demo_mode 上会有两种错法：接了真源还带着「示意」，或者演示时手一抖把没接真源的标关掉了。
后者是事故，前者是长期说谎。

### 地基问题（这一版必须先解决的那一件）

车辆页现在写的是 `"412 km"`、`"3/4 箱"`、`"2.4 / 2.4 / 2.3 / 2.5 bar"`、`"23,417 km"` ——
**四个字符串，写死在 Composable 里**（`apps/android/src/main/kotlin/.../ui/SceneCards.kt:37-40`）。

规则引擎读不到字符串，屏也拿不到，接真源那天还得把界面重写一遍。所以第一步不是画界面，
是把它们升成 `core/vehicle` 里带 `source` 和 `takenAt` 的读数，卡片改成**渲染读数**。
这一步做完，「示意」那个标才第一次变成数据驱动而不是美术。

## 4. 第一版就这 6 条

不多。6 条里 4 条现在就能算，2 条靠录入。

| # | 条目 | 触发 | 判据来源 | 界面上怎么说 | 严重度 |
| --- | --- | --- | --- | --- | --- |
| 1 | **胎压偏低** | 任一轮 < 标定 −0.2 bar | `nominal` + 读数 | 「左后 2.3 bar，标定 2.5」→「补气到 2.5」 | 差 0.2~0.4 = soon；>0.4 = due |
| 2 | **常规保养到期** | 里程 − 上次保养里程 ≥ 间隔 | `manual` + `user` | 「距上次 9,817 km，手册 10,000 km」 | 差 5% 内 = soon；超了 = due |
| 3 | **空调滤芯** | 里程/月数到点，**且**车主勾了「车上有孩子」 | `manual` + `user` | 「上次换是 2026-03，跑了 19,400 km」 | 有孩子上调为 soon，没有 = note |
| 4 | **长期停放** | 连续 ≥ 7 天里程增量 < 20 km | `observed` | 「这周基本没动」→「一周开一次，十分钟」 | note |
| 5 | **卫星额度包** | 额度水位 < 20% 或未来 7 天填了偏远出行 | 真接的额度页 | 「还剩 3 条」→「加包」 | soon |
| 6 | **车载应急包** | 车主勾了「车上没有急救包」 | `user` | 「呼救发得出去，车上没有能用的东西」 | note |

第 3 条是**跨场景联动**：它同时是车辆页的一条和家人页的一条（同一份记录，视图按页 —— 沿用 D11）。
第 5、6 条是这一版里**仅有的两处"商品"**，理由见下面。

### 4.1 为什么额度包和应急包可以放，别的不能

- **额度包**：信号是真的（额度页我们本来就接了），履约也在我们自己手里 ——
  你 2026-11-05 说了**卫星通信可以开**，所以这条从"发申请"升级成真入口：水位到阈值直接进加包流程。
  还缺的是**开通动作长什么样**（自助页面 / 找运营 / 有没有 API），拿到那个我就把落点接上（◆4）。
- **应急包**：它不是推销，是**产品自洽**。App 有呼救功能而车上没有能用的东西，这是缺环。
  判据是车主自己勾的，兑现是一张本地清单，不接电商。

除这两条之外的任何"商品"，在这一版里都只到**工单上的一行字**为止，不出现价格、不出现购买按钮。

### 4.2 等信号的（明确不做，这一段比上面那张表有用）

| 条目 | 为什么不做 | 要什么才做 |
| --- | --- | --- |
| 雨刮 | 没有任何磨损信号 | 雨量传感器或前挡摄像头，都没有 |
| 刹车片 | 没有厚度读数。**而且这是安全件，猜错的代价不对称** | 轮端/制动传感或门店回检数据 |
| 机油劣化 | 我们是按里程算的，不是按油液状态 —— 那条归到 #2 常规保养里说 | 油液传感 |
| 动力电池健康 | 只有 30 天平均电耗，算不出 SOH；SOH 需要充电曲线 | 电池管理系统的真读数 |
| 保险 / 延保 / 金融 | **不做，不是"以后做"**。需要资质，而且和「卫星兜底」这个定位互相拆台 | —— |

## 5. 措辞红线（安全件这一段单独拿出来）

1. **只报读数与标定差，不下诊断结论。**
   「左后 2.3 bar，标定 2.5，偏低」可以说；「轮胎不安全」「有爆胎风险」不可以 ——
   我们没测胎面，那句话是编的。
2. **不许出现「已为您预约」「门店已确认」「已下单」「已发货」。**（沿用既有文案红线，这一版是新增高危区）
   工单发出去只可以说「已发出申请」，且必须带时间。
3. **时限类判据不许写成后果。** 「手册要求 10,000 km」可以；「再不保养会拉缸」不可以。
4. **儿童相关只按车主填的身高/年龄说，不按行为数据猜。** 这一版没有安全座椅推荐，
   只有空调滤芯那一条因为"车上有孩子"上调优先级 —— 这个区别要守住。
5. 每条建议旁边那个来源标，**字号不许小于 12sp**。它是这一版的产品主张，不是脚注。

## 6. 闭环：工单走卫星短报文

这是这一版唯一一条**真能演示到底**的路，也是把「卫星通信」和「养车」这两件本来不相干的事
缝在一起的那一针。

### 6.1 为什么必须编码，不能发中文

L1 档按最坏口径（`LengthUnit.HEX_CHARS`）算：数据字段 45 B，骨架 20 B + 分片头 1 B，
**一片只剩 24 B 载荷**。一条中文清单按 UTF-8 少说 150 B，得拆 7 片，而分片在演示现场是最容易掉的一环。

所以发的是**索引码**，不是文本。人读的那份全文留在手机上。

### 6.2 编码表（固定 21 B，一片发完）

```
偏移  长度  字段            说明
0     1     tag             0x03 = maint_workorder（新值，见 §6.4）
1     1     ver             0x01
2     3     vin6            VIN 后 6 位，BCD 压缩
5     4     odometer        累计里程 km，小端
9     4     date            生成日：年 2B + 月 1B + 日 1B
13    8     items           最多 8 项，每项 1B 规则码（就是 §4 表里的 Rule.id 映射）
                            0x00 = 空位；高位 bit 存 severity 的 2 位
21    —     合计 21 B ≤ 24 B ✓
```

被叫号码在帧头里，不占这 21 字节。

### 6.3 接收方是谁 —— 这条必须说清

**接收方是我们的彩排台，不是真门店。** 门店拿到这 21 字节解不出来，因为码表在我们手里。

所以 M2 的交付物里有一半在屏侧/第三台机器上：**彩排台加一个工单解码视图**，
把收到的 21 B 还原成「保养 / 胎压 / 额度包 · 23,417 km · VIN 88213 · 11-05」。
演示现场那一屏是这个功能的全部说服力所在 —— 手机上勾三项，卫星发出去，另一台机器上清单长出来。

界面上不许出现"已发送给门店"。写「已发出 · 接收方：演示接收台」。◆3

### 6.4 传输侧要动的东西（很小，但要动）

- `SosFrame` 那套 EXT 骨架**不改**，只加一个 `tag` 取值。分片、序号、校验全部复用。
- 上行不是 SOS，优先级要排在 SOS 之后 —— 复用现有队列，不许新开一条绕过 TPI 写锁的路。

## 7. 隐私档 × 推荐

现有三档里最严那档是「本地留存，仅 SOS 出网」。这一版给它一个明确的说法：

- **推荐全部在手机上算。** 规则引擎是本地的一段 Kotlin，没有云调用，也不需要模型。
  AI 网关在这里唯一允许的活见 §8.4。
- **`本地留存` 档下，工单不许走卫星上行。** 只有本地生成 + 复制/系统分享。
  用户当场点「发接收台」时，**先弹出那 21 字节的明文清单**再确认 —— 出网的内容要看得见，
  这一条比"我们重视隐私"那句话有用。
- **里程 + VIN 后 6 位合起来是可识别信息。** 所以工单里放的是后 6 位而不是全 VIN，
  而且这一条要写进隐私说明页，不是只写在这里。

## 8. 界面落点

### 8.1 App（我做）

| 位置 | 是什么 |
| --- | --- |
| 车辆页顶部 | 一张「该做的事」卡：最多 3 条，每条两行（读数 / 判据 + 来源标）+ 一个勾选框。多于 3 条给「还有 N 条」下钻 |
| 车辆页 → 清单页（新） | 全部建议、勾选、生成工单、三个出口：复制 / 系统分享 / 发接收台（走 §6） |
| 设置里 | 上次保养里程与日期、车上有没有急救包、车上有几个孩子多大 —— **能填的输入框比一个假 API 诚实** |
| 首页 | 只在有 `due` 或 `soon` 时出一行，挂在状态条下面。**不新增卡** —— 首页已经有圆屏镜像那块大卡 |
| 家人页 | #3 空调滤芯那一条按 D11 归页，同一份记录，不复制 |

车辆页那句副标题本来就是「用车养车 · 卫星兜底」，这个功能落在这里不需要新起 Tab。

### 8.2 圆屏（屏侧机器）

- `UiCard` 加一档 `maint`：一行字 + 脸切 `worried`（`due`）或 `neutral`（`note`）。
  1.75" 的屏装不下"读数 + 判据"两行，所以**屏上只说该做什么，不说为什么** —— 为什么是手机的事。
- **屏不许自己算推荐，也不许自己挑哪一条。** 定内容的权在手机的 `CardPolicy`，和现有那一套一致。
- **老固件不能收到画不出来的枚举值。** 所以 `maint` 这一档只在 `hello.protocols` 协商出
  **v3** 时才发 —— 和 v2 过滤 `dialog` 是同一套机制（`ScreenCodec.negotiated`）。
  没申报 protocols 的固件按 v1 处理，永远收不到 `maint`。这是加性变更，不破坏任何现有连接。

### 8.3 GT1005 / 其他硬件

- 真车况的最终来源是 **TBOX / OBD / 车厂云**，不是卫星。卫星只兜底 SOS 和这一条工单上行。
  这条要在产品说明里写死，否则观众会以为养车数据也是卫星来的。
- **具体买什么、能拿到哪几项、拿不到的是哪些，全在 `docs/VEHICLE-DATA.md`**。
  一句话版：标准 OBD 只给 VIN 和油量，**胎压要走独立 BLE 传感器（¥150 那档）**，
  续航/SOC/总里程要车厂云 —— 别指望一个盒子解决四项。
- 接进来是 `core/devices` 的第三种设备，读数生产者，**规则引擎一行不改**。

### 8.4 AI 网关在这条链上的权限（写死，不给现场留口子）

规则引擎出候选 → **模型只许做措辞合并与排序，不许新增候选、不许改判据、不许改严重度**。
落地上是一条硬约束：模型的输出必须能对上某个 `Rule.id`，对不上就丢，界面上出现的仍是规则那条。
理由和 §1 第 2 条是同一个：这一版的全部可信度押在判据上。

## 10. 验收判据（可测的，不是"看着不错"）

1. **没有无依据的建议**：测试遍历所有 `Suggestion`，断言 `evidence` 非空且 `rule.thresholdSource` 非 null。
2. **本地档零出网**：`privacy = 本地留存` 下跑完整规则引擎 + 生成工单，断言没有任何网络/模组调用记录。
3. **一帧装得下**：工单编码在 L1 最坏口径下 ≤ `MessageBudget.chunkBytes`，用真预算算，不写常数。
4. **老固件不受影响**：`protocols = null` 的连接永远收不到 `UiCard.maint`。
5. **模型不越权**：给网关注入一条"凭空多出来的建议"，断言界面上不出现。
6. **读数缺失时不硬说**：删掉胎压读数，断言 #1 那条**整条消失**，而不是变成「数据不足」占一行。
7. 界面截图凭据：车辆页有数据 / 无数据 / 隐私档本地 / 清单页已勾选待发 四张，字号 1.3 那一档必拍。

## 11. 需要你给的三样东西 ◆

1. **◆1 真保养手册参数**：常规保养间隔（里程 + 月数）、空调滤芯间隔、标准胎压。
   吉利/极氪哪一款车为准？没有的话这一版全部按示意值走，界面上就一直挂着「未接手册」那个标。
2. **◆2 到底有没有真商品**：额度包是不是真能开？如果有，#5 那条的兑现方式要从"发申请"改成真入口。
3. **◆3 工单的接收方在演示现场叫什么**：写「演示接收台」还是写一个具体的人/门店名。
   我按红线默认写前者，你要后者我就改，但"已发送给门店"这句无论如何都不会出现。
4. **◆4 车厂云接口能不能开、找谁开**，以及**额度包的开通动作长什么样**。
   这两条合起来决定这一版最后是"半真"还是"全真"：
   前者管续航/SOC/里程，后者管第 5 条能不能从"申请"变成真入口。
   详见 `docs/VEHICLE-DATA.md` §2 路 1 和 §7。
5. **◆5 知识库资料的形态**（手册扫描件 / 结构化表格 / 能导出的系统），给一份样例就行。
   我照它定 `VEHICLE-DATA.md` §5 那个格式，别让我猜一个格式让你返工。

## 12. 不做清单（写下来是为了防止以后被当成"漏了"）

- 电商下单、支付、优惠券、门店预约确认。
- 保险、延保、金融类产品推荐。
- 任何"根据驾驶习惯给你推荐"的画像类东西。
- 刹车/转向/轮胎磨损的诊断结论。
- 云端跑推荐（至少这一版：规则在手机上，判据在仓库里）。
