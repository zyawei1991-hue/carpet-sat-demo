## D9 · 彩排台：假时钟驱动器 + JSONL 回放截图

**状态**：生效

`simulator/` 起的是同一条 `:core` 业务链路，只换两样：时间用假时钟（1 tick = 1 假秒 = 真时间 600ms），
过境窗口按真机 12 分钟建模。这样"星升起来"这种分钟级事件能在几十秒里彩排完，
而倒计时、窗口开合、重发次数这些相对关系保持真实。

判据窗口用的是**彩排阈值**（`DemoDriver.demoPolicy()`：6 秒确认、3 秒探测、6 秒 ACK 超时）。
生产阈值仍然只在 `protocol/link-policy.md` 里定死，代码里不复制一份 —— 现场彩排一定要调时间，
但调的是演示参数这件事必须一眼看得出来。

截图不抢 WebSocket 首帧：驱动器把出站消息原样录成 `shots/*.jsonl`，
headless Chrome 打开 `screen.html?replay=xxx.jsonl` 回放后定格。
这台机器上 ws:// 还要先躲开系统代理，抢帧子不稳，回放是确定的。

**顺手定死的四条不变量**（都是彩排台暴露出来的，不是先想好的）：
1. `seq` / `event_id` 只能在 `DemoRuntime.push()` 一处盖。蜂窝和卫星各自计数的话，
   展示端按 seq 检测丢包、按 event_id 去重会撞车 —— 撞一次就是白丢一条 SOS
2. 探测包由状态机"要求发"（`ProbeRequested`）不等于"发出去了"，得有 `drainProbe` 真的走一趟模块
3. `RECOVER → CELL` 只能由"队列真的排空"触发（`QueueDrained`），否则补发没完成就回蜂窝，攒下的会烂在队列里
4. `hello` 必须有回执，且回执只回给那一条连接（`sendTo`），不能广播位置状态给还没通过白名单的客户端

**被推翻的条件**：真机到货后如果假时钟和真时钟的行为分叉（比如 `txLatency` 在假时钟下被忽略），
彩排结论就不能信了 —— 届时 `SimulatedModem` 的时延要接到假时钟上，或者干脆只保留单测、丢掉截图链路。

## D8 · 展示端接入用明文 ws，不用 wss

**状态**：生效（演示期）· **量产前必须重新评估**

`protocol/screen-link.md` 原写的是 HTTPS/WSS :8443 自签证书。实现时改成 `ws://` :8443，理由：

- 圆屏侧要连自签证书，固件得引入 TLS 栈并显式关掉证书校验。ESP32-S3 上这条路径能吃掉可观的 PSRAM 和握手时间，而"关掉校验的 TLS"提供的安全性接近 0
- 手机给自签证书要么在构建期固化 keystore、要么运行时生成，两条路都把 W2 的工期花在一条没有真实威胁模型的链路上
- 链路只在演示现场的局域网/热点内，不出公网

**替代控制（三层，代码里都已落地）**：
1. `ScreenLinkServer.accepting` 默认 false —— App 上必须手动打开"允许展示端接入"才收连接
2. `screen_id` 白名单，非白名单首帧 `hello` 直接 close
3. 服务只在 `DemoRuntime.start()` 后监听，Activity 销毁即停

**被推翻的条件**：任何一条成立就换回 wss 或加 mTLS —— 展示端接入点可能出内网 / 演示数据里出现真实车主信息 / 通过安全评审要求传输加密。届时把 `accepting` 换成配对码机制。

## D7 · 传输抽象 SatelliteModem，先跑 Simulated

**状态**：生效

App 不直接调 SDK 的 `DispatchManager`，中间加一层 `SatelliteModem`（suspend 接口，见 `core/.../modem/`）。三个实现位：`SimulatedModem`（已实现）、`UartModem`（RS232 + USB 转 TTL，BLE 文档没到时的 Plan B）、`BleModem`（BLE 协议文档到手后）。

理由：§10 风险表里"GT1005 BLE 协议文档延迟"标的是高影响阻塞。把传输做成可注入的，业务链路（链路状态机、SOS 重试、心跳排队、展示端推送）就能在**硬件和 SDK 都没到货**的现在全部写完并单测。W2 换实现时 `DemoEngineTest` 的断言不应该改。

同时它给了一个副产品：`SimulatedModem` 的过境窗口可调，彩排时能人为演"没过境 → SOS 三次无 ACK → 展示端弹红字 + 下次过境倒计时"这条最难自然复现的分支。手机 App 也接了这三个开关（模拟断网 / 模拟未过顶 / 模拟终端掉线），所以硬件到货前手机本身就能整套演示。

**进展**：`UartModem` 已落地（`core/.../modem/UartModem.kt` + `LinePort`）。分界线画在
"和指令表无关" 与 "指令表" 之间 —— 前者（半工口一次只压一条在飞、没回话算 FAIL、
回了 NO_ACK 才算星上未确认、主动上报不能被当成应答吃掉、口没开就一个字节都不往串口上写）
已经写完并单测；后者集中在 `Gt1005Verbs` 一个类里，**那一版是按 SDK 暴露的动词名（ICI/SFQ/CEQ/CEI/MCI/GMO/TPI）
猜的，没有一条经过真机确认**。串口文档到了只改 `Gt1005Verbs`，`UartModemTest` 的断言应该原样通过 ——
通不过就说明骨架里混进了猜测，那是要改骨架。

**2026-10 的后续：这条预言应验了，但应验的方式是整张表被删。** 时空道宇 SDK（两个 aar + 28 页《通用数据接口规范 V1.0》）到手解完后确认：协议是 **NMEA 风格 ASCII 语句**（`$CCXXX,…*hh<CR><LF>`，`$` 与 `*` 之间逐字节异或），不是我们以为的二进制帧。于是：

- `Gt1005Verbs` **整张删除**，语句组包/校验/解析由 `GsatSentence` + 厂商 `DispatchManager` 负责；
- `UartModem` **退化成纯字节管道**（`send(byte[])` / `receive(byte[])`），正是 D7 当初预留的那个形状 —— SDK 自己不做 IO，所以 UART 路线合法，BLE 只是官方 demo 的一种实现；
- 协议语义上移到 `SentenceModem`（上电会话 DII→ICI→TPI→PDI、按 ICI 的 `serviceType` 分叉收信状态机、升级期全局写锁 `ModemGate`、TPI 周期任务 `TpiTracker`），业务侧仍只认 `SatelliteModem`；
- `FakeGsatModule` 按规范的字段序号组包，`SentenceModemTest` 因此同时是**那份 28 页文档的一次可执行翻译** —— 真机到货那天变的只有管道。

值得单独记一笔的两个"没硬件才撞得出来"的坑：① SDK 的 `updateLocation(经, 纬)` 和语句里的 `(纬, 经)` **顺序正好相反**，传反了编译不报错，要到外场才发现定位在地球对面 —— 所以坐标现在只允许以 `GeodeticPosition` 这种**带字段名的类型**传递，裸 `double` 入口全部封掉；② 星上 ACK ≠ 核心网收到 ≠ 平台受理（〔规 §3.1.4 注6〕），判序写成 `contains("ACK")` 就会把"没确认"演成"已送达"，这是 §6.1 红线一的由来。

写这一步时踩到过一个真会咬人的坑：`NO_ACK` 以 `ACK` 结尾，判序反了就把"星上没确认"读成"已送达"。
这类错误只有在没硬件时先把骨架写出来、再拿假口去撞才会暴露，等接上真机就是现场翻车。

**被推翻的条件**：SDK 的 `ModuleOperation` 接口形状与本抽象差异大到需要适配层重写，或卫星时延模型（分钟级）无法用 suspend 表达。

## D6 · 构建分层：core 纯 JVM + app 薄壳

**状态**：生效

```
:core  纯 Kotlin JVM。协议编解码、链路状态机、SatelliteModem、DemoEngine。零 Android 依赖。
:app   Android 薄壳。定位、蜂窝探测、WebSocket 服务、按钮。只做"喂输入 + 推输出"。
```

理由：业务链路必须能在 CI 上跑，不能等真机和模拟器。目前 `:core` 有 32 条测试，其中一条直接读 `protocol/examples/*.json` 做三方契约对拍，另一条断言 Kotlin 编出的帧与 `protocol/sos_frame.py` 的黄金 hex 逐字节相同。

配套约束：
- **时间从外部注入**。链路状态机、SOS 重发、过境窗口全部接受 `nowMs` / `MonoClock` / 可替换 `sleep`，没有一处读系统时钟
- **假时钟推进用相对时长**，不用绝对终点。踩过一次：测试起始时钟改到 2026 epoch 之后，写死 `untilMs = 25_000` 的用例静默零次循环、假通过
- `minSdk = 26`（文档 §3.1 写 Android 24+，但星历 SDK 要求 26+，取严的）
- 不引 androidx / Play Services。UI 全代码搭，定位只用 `LocationManager`

工具链不在仓库里，靠本机 `C:\Users\Administrator\sdk\env.sh`（JDK 17 + Android SDK + Gradle 8.7）。换机器时这套要重建；`gradle/wrapper` 的 distributionUrl 指向华为云镜像，`services.gradle.org` 在这台网络上直连不通。

## D4 · 展示端数据通道：从「拉云端 REST」改为「直连手机局域网服务」

**状态**：生效 · **需要回写架构文档 §4.2 / §5.3 / §6.1 / §6.2**

原方案里圆屏「Wi-Fi 连云端 REST API 拉数据」。演示阶段不建业务后端，这条不成立，改为：

**手机 App 在局域网内起 HTTP + WebSocket 服务，圆屏直连手机，不经过任何公网服务器。**

- App 侧监听 `0.0.0.0:8443`，自签证书，圆屏侧跳过校验（演示设备，可控）
- 状态推送走 WebSocket（1 Hz 心跳 + 事件即时推），轨迹/地图切片等批量数据走 HTTP GET
- 组网三种模式，按现场条件降级：
  1. 现场有可用 Wi-Fi → 手机和圆屏连同一个 SSID
  2. 现场无网 → 手机开热点，圆屏连热点（Android 可同时开热点并保留蜂窝数据）
  3. 连热点也不稳 → 手机直接 `adb reverse` 或圆屏连手机的第二个 AP，纯局域网，不要公网

**这样做的收益**：地下停车场、野外这些蜂窝断掉的场景，展示端依然能出画面。原方案在这些场景下展示端会白屏——这是评审时标过的缺陷，改完顺带修掉了。

**代价**：圆屏拿不到"云端"数据，所以所有需要跨设备持久化的功能（车主远程查看、多用户、云端轨迹归档）演示阶段一律不做。见 D3。

## D3 · 演示阶段不建业务后端，能力边界确认

**状态**：生效

逐条对照 §5.2 功能清单，判定哪些不需要后端也能满足：

| 功能 | 优先级 | 不建后端能否做 | 落在哪 |
|---|---|---|---|
| BLE 连 GT1005 + SDK 初始化 | P0 | ✅ | App |
| GNSS 定位（手机 + GT1005 融合） | P0 | ✅ | App |
| 4G/5G 位置回传 | P0 | ⚠️ 语义变更 | 原来是"回传云端"，改为"回传展示端"（D4）。卫星那一路仍回时空道宇测试平台 |
| SOS 一键（MCQ + 4G 双发） | P0 | ✅ | 卫星路走测试平台；4G 路走 App→展示端局域网推送 |
| 离线心跳 SFQ 定时 | P0 | ✅ | App 定时器 + 卫星 |
| 电子围栏 + 越界告警 | P1 | ✅ | App 本地算。GeoJSON 存本地，手机 GPS 逐点判断，不需要服务端空间查询 |
| 轨迹记录 + 回放 | P1 | ✅ 降级 | App 本地 SQLite；回放推给展示端。**不做**云端归档和跨天跨设备查询 |
| 卫星过境预测 | P1 | ✅ | 星历 SDK 在 App 端本地计算 |
| 离车哨兵 | P1 | ✅ | App 加速度传感器，本地 |
| 4G/卫星自动切换 | P1 | ✅ | App 本地状态机 |
| 宠物状态（情绪/温度/电量） | P2 | — | 本来就没传感器，不做 |

**仍然依赖外部、但不是"我们自建后端"的三项**（这三项是真正的进度风险，不是工作量问题）：

1. **AI 语音对话** —— 走小智官方云（ASR+LLM+TTS）。要求演示现场能出公网。公共服务器不稳定，§10 已列备选：圆屏只做屏幕显示，语音对话挪到手机 App。**建议 W5 彩排时实测一次，别等到演示当天。**
2. **卫星链路平台侧闭环** —— SOS 被平台收到、平台下发 MCI，依赖 §8.1 的**测试卡 + 测试账号 + SOS 平台侧对接方案**。这是外部排期，W1 就要催，不催就是 W3 卡住。
3. **GT1005 BLE 协议文档** —— UUID / 帧格式 / 分包规则。§10 的对策（先用 RS232 + USB 转 TTL 走有线）是对的，但要注意 SDK 的 `ModuleOperation` 接口只要求 `send(byte[])` / `receive` 回调，**传输层可替换**。所以正确做法是 W1 就把 `ModuleOperation` 的两个实现都写掉（`BleModuleOperation` + `UartModuleOperation`），BLE 文档没到就用 UART 版跑全部业务逻辑，文档到了换一个注入。**这样 BLE 文档延迟不再是阻塞项。**

**明确放弃的（演示阶段）**：车主远程查看、多设备多用户、轨迹云端归档、围栏规则远程下发、SOS 短信/电话外呼。

## D2 · 双通道链路拓扑（先试）

**状态**：试验中，W2 末验证

圆屏和手机之间**结构化状态走局域网 WebSocket/HTTP**（见 D4），**语音走小智云 Wi-Fi**，两条通道独立。

理由：卫星链路本身就是断网场景，展示端的控制面不能依赖公网；但语音流 BLE 带宽扛不住，且小智固件的语音链路是现成的，不改。

**验证标准**（W2 末）：手机 App 杀掉再启动，圆屏画面在 3 s 内恢复链路状态显示；期间语音对话不中断。达不到就说明两条通道有干扰，回退到"圆屏只读 WebSocket、语音降级"。

## D1 · 展示端硬件选型

**状态**：生效 · 已下单

`ESP32-S3-Touch-AMOLED-1.75` **带外壳版（1.75-B）**，不是文档 §1.2/§4.1/§7 里写的 1.75C。

变更原因（评审时确认）：
- 1.75C 只引出焊盘、无 8PIN 排座，且封在 CNC 壳里，做不了模块化底座
- 1.75-B 后盖给 8PIN 排母、SPK、BAT 各开了窗口，接口可外接
- 1.75-G 与带外壳互斥，且定位源本来就是 GT1005，圆屏不需要独立 GNSS
- 两款都在小智固件 `USE_DEVICE_AEC` 白名单内，语音能力等价

**需要回写文档**：§1.2 角色表、§4 整章标题和 §4.1 规格表、§7 BOM 第 2 行、§8.3 样机申请项。

**BOM 补充**：1.75-B 配置清单只有「板 + 8Ω 2W 喇叭」，**电池不随盒**，要另购 3.7V 锂电 + MX1.25 2P 插头线。
