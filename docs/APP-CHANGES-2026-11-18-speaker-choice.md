# App 改动单：发声设备选择对「屏上起头的对话」也生效 + 答句音频是全零静音（2026-11-18）

**提出人：owner（原话）：「现在圆屏的扬声器坏了，能不能做成 APP 上也能选择，由手机发声还是圆屏发声」。**
**【当晚更正】扬声器没坏**：屏侧放 `>audtest 2` 测试音（`level 0.95`），owner 当场听见。
他听不见答句的真因是下面 §A 那条：**手机推过去的答句音频内容是数字静音**。
选择格这个需求 owner 仍然要（硬件随时可能真坏、人也想随时换手机念），照做；
这条**覆盖** 2026-11-11 那条「屏上对话只由圆屏念（无例外）」。新规矩：

> **齿轮面板「由哪个设备发声」那一格对所有对话生效（屏起头、手机起头都一样）。
> 默认仍是圆屏；选了「这台手机」就只由手机念；屏没连/没升到 v3 时照旧落回手机。
> 任何一轮都只允许一个设备出声（这条不变）。**

## 现状（代码里已经有什么）

- 选择格**已经有了**：`ScreenVoice._screenDevice` / `setScreenDevice()` / `ScreenDevice{screen,phone}`，
  齿轮面板已接。`answerHere()` 已按它路由 —— **但只对手机起头的轮子生效**。
- 屏起头被写死强制屏念：`ScreenVoice.speak()`（apps/android/src/main/kotlin/com/carpet/satdemo/app/ScreenVoice.kt:333-343）
  里 `origin == screen` 那一支直接 `screenOnly = true`，绕过选择格。这就是要改的地方。

## 要改的（就一处路由 + 一处护闸）

1. **`speak()` 删掉屏起头强制屏念的特判**：所有 origin 一律走
   `synthesizeAndSend(turnId, body, origin = origin)`（screenOnly 缺省 false）。
   路由交给已有的 `answerHere()` / `wantScreen`（941bd54 那版 `wantScreen = screenOnly || !answerHere()`
   不用动 —— screenOnly 从此恒 false，它自然退化成 `!answerHere()`，正是新规矩）。
   注释里「不受发声设备设置影响」那段同步改写成新规矩，别留旧规矩误导下一个人。
2. **护闸：选了手机发声时，屏开始新一轮录音就把手机播放停掉。**
   屏侧起轮是无条件 `carpet_audio_abort`（停嘴留账），手机侧没有对应动作的话，
   上一句答话会从手机喇叭录进下一句问话里。落点：收到**新 turn_id 的第一帧 mic_chunk** 时
   （AppRuntime.onMicSegment / MicUplink 收齐处之前）调 `stopPhonePlayer()`。
   屏起头轮选圆屏发声时这条无副作用（手机本来就没在放）。

## §A 更要紧的一条：答句音频推到屏上的是**全零静音**（新发现，优先查）

11-18 夜真热点第一轮（turn m-fbee4c-1，答句「拜拜！」）屏侧录音：

```
@audio at 32000/59904 level 0.00        ← 播放进行中的实时 RMS = 0
@audio 放完 59904 字节 / 1.9 秒
>carpet: @audio turn=m-fbee4c-1 played=59904/59904 frames=24 drops=0 gaps=0
```

同一块板同一晚的 `>audtest`/`>audgap` 台架音 `level 0.93–0.95`，owner 也**听见了**测试音
⇒ 喇叭、I2S、播放任务、b64 解码整条屏侧通路都是好的；**那 59904 字节 PCM 内容本身就是零**。
owner 因此误判「扬声器坏了」。屏侧 `level` 量的是正在写进 codec 的样本（carpet_audio.c player_task），
不是估计值，这条证据是硬的。

仓库里 `NetVoice.pcm16k` → `AudioChunks.toMono16k` → `commands` 逐行读过，没有会产零的地方
（le16 无符号→toShort 回绕对单声道是恒等；重采样插值正常）。所以嫌疑在：
**装机那版 APK 的解码/TTS 路**（装机版号未知，可能旧于仓库），或 **TTS 返回的 MP3 本身是静音**。

要做的：
1. `playNetAnswer` 里 `pcm16k` 成功之后、`commands` 之前，加一行日志：
   `屏幕语音：解码 PCM ${pcm.size} B，peak=<绝对值峰值>`（遍历一遍取 max abs，和屏侧 mic peak 同一个算法）。
   这一行把「TTS/解码出了零」和「传输/屏侧出了零」当场分开。
2. 同一行顺手带上 `mp3.size` 和 TTS 来源（edge-tts / baidu / 本机），静音时好追是哪一档回来的。
3. 装新 APK 再测一轮：peak=0 ⇒ 查 TTS 响应/解码（把 MP3 存一份到日志目录可复现）；
   peak>0 而屏 level=0 ⇒ 才轮到查传输（目前无此迹象）。

## 不用改的

- **屏侧固件一行不动**：App 不推 audio_chunk 它就不出声，字幕/口型照旧（口型会跟着假播放走，
  可接受；别为这个改固件）。
- 不加新页面/新按钮（选择格已有）；APK 不许变大；四张表不动。
- 默认值不动（仍是圆屏）——owner 自己会在齿轮里选「这台手机」。

## 验收口径（装新 APK 后，热点连着屏）

1. 齿轮选「这台手机」→ 点屏上 Avatar 说一句话 → **答话只从手机出**，屏不出声；
   屏串口 `>carpet` 的 `@audio frames` **不涨**（证明音频帧根本没推屏，不是推了没响）。
2. 齿轮选「圆屏」→ 同样一轮 → 音频帧照旧推屏（`frames` 涨），**且 owner 真听见**
   （喇叭已确认是好的；但要先修 §A 的静音问题，否则推过去也是零）。
   屏侧 `played=…` 只证明电信号送到位，听感验收以 owner 耳朵为准。
3. 任何一轮不许两个设备同时出声；手机在放答话时对着屏说下一句，手机立刻停嘴（护闸 2）。

## 背景数字（11-17 夜真热点第一轮，屏侧录音实测）

点 Avatar → 免按键 3.60 s → `上行 49/49 帧、125440 字节 0.69 秒发完`（peak=1120 真人声）
→ **22.9 s 后**文字答句回屏 → 屏 `放完 59904 字节 drops=0`（**但内容全零，见 §A**）。链路整条是通的；
「时间好长」的大头在手机侧那 22.9 s（转写+模型），与本改动单无关，
拆段靠 941bd54 已加的转写耗时日志（装机版还没有，**这版 APK 要一起带上**）。
