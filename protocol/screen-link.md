# Screen-Link 传输规范 v0.2

消息格式见 `screen-link.schema.json`，本文件只讲怎么传。v0.2 加的是版本协商与对话通道，第三轮加的是音频通道（契约号 3），其余没动。

## 拓扑

手机 App 是**服务端**，展示端是**客户端**。反直觉，但正确：App 是数据源，且展示端不需要被外部寻址。

```
展示端(1.75-B)  ──Wi-Fi──►  手机 App (WebSocket, :8443)
      │
      └──Wi-Fi──►  小智官方云（语音 ASR/LLM/TTS，与上面完全独立）
```

两条 Wi-Fi 连接走同一个 AP，互不依赖。见 DECISIONS D2/D4。

## 通道

| 通道 | 协议 | 用途 | 频率 |
|---|---|---|---|
| 控制面 | WebSocket (`ws://`) | `hello` / `state` / `event` / `command` / `ack` | state 1 Hz；event 即时 |
| 对话面 | 同一条 WebSocket，不另开端 | `dialog`（契约 v2） | 说话时；静默时 0 |
| 音频面 | **同一条 WebSocket，不另开端**（为什么不 UDP 见「音频通道」一节） | `command{audio_chunk}`（契约 v3） | 答句念出来那两三秒；其余 0 |
| 批量面 | 暂未实现。`track_pull` 现在只在契约里占位，轨迹数据还没给展示端读 | 按需 |

## 会话建立

1. 展示端启动 → 读配网信息 → TCP 连 `:8443`
2. 展示端发 `hello`，带 `screen_id` / `fw` / `dock_type` / `protocols`
3. App 校验 `screen_id` 在白名单 + `protocols` 与本端 `SUPPORTED_VERSIONS` 有交集 → 回 `ack`，开始 1 Hz `state` 推送
4. 版本不兼容或 id 不认识 → App 直接 close（policy code 1000），展示端显示黄屏而不是崩溃

### `hello` 里的电量与底座

`battery_mv` 现在真的会发，但它的语义比字段名窄，用之前得知道三件事：

- **一次连接只读一次**：值在 `send_hello()` 里现读，所以断链重连之后带的才是新数。中途换电池**不会**推给 App —— 契约里没有第二帧承载它。要在屏上持续报电量，得往 `state` 里加字段，那是另一轮改契约。
- **省略而不是发 0**：没装电池 / 没读到 / 系数没对上时这一项整块不进帧。App 侧 `batteryMv == null` 显示的是「外接供电」，发 0 会被读成「电池空了」，两者在展台上是完全不同的两句话。
- **毫伏值未经标定**：固件按 AXP2101 的 1.1mV/LSB 折算，但厂商例程把同一个原始值当纯 mV 打印，两份说法冲突，实机接上电池后必须拿万用表量 BAT 座两端对一次。对不上只改固件那一行，不改契约。

`dock_type` 目前还是固件里写死的字符串，板上没有识别底座的电路。**别照"8PIN 分压电阻 + ADC"去做**：
8PIN 引出的 GPIO16/17/18 在 ESP32-S3 上属于 ADC2，而 ADC2 与 Wi-Fi 共用、联网时官方不支持采样，
这条板上唯一常驻的联网方式就是 Wi-Fi。真要做硬件身份，两条可行的：
① 三个脚当输入 + 内部上拉，底座把其中几个短接到 GND → 3 位编码刚好盖住 `dock_type` 的 7 个取值；
② 干脆不 sensing —— 底座是谁装的就是谁，由 App 在配对时选，`dock_type` 走 `command` 下行写进 NVS。
在只有 1-2 个底座之前，②是正确答案。

## 版本协商

**协商看 `hello.protocols`，不看帧上的 `v`。** 两个原因：出站帧走了 `encodeDefaults = false`，`v` 不总是写出来；更要紧的是老固件本来就不懂 `v` 是什么，拿它当依据等于要求对端先升级才能被识别。

- `protocols` 省略 = **不申报** = 按 v1 待。这条默认值不能是当前版本，否则新加一档时所有老固件都会被误判成新固件
- 取双方都支持的**最大值**作为本会话协商结果，记录在连接上（`ScreenLinkServer.negotiated`）
- v1 → v2 **只多一种帧**（`dialog`），state / event / command / ack 一字节未变。所以 v1 固件不用升级也能继续看状态，只是这台屏不接对话
- v2 → v3 **不多一种 `t`**：音频骑在已经存在的 `command` 上，另外两项（`ui.card=maint`、`hello.screen`）是可选加性字段。所以 v2 固件不用升级也能继续看状态、继续对话，只是没声音、maint 那一档退回 status、不报几何
- 逐连接过滤：`broadcast` 时版本 < 2 的连接收不到 `dialog` 帧，版本 < 3 的连接收不到 `command{audio_chunk}`。不然老固件的解析器会撞上一条它不认识的 `t`

## 对话通道（契约 v2）

这条是这次加的重点，因为它决定了一个产品问题：**"跟车说话"这件事的主场景在圆屏，而对话记录的宿主在手机。**

为什么宿主必须是手机，三条都成立才敢这么定：

1. 对话要回答的全是状态类问题（车到哪了、还剩几条额度、下次过境几点），**事实全在手机那台状态机里**，屏侧只有 1 Hz 的投影，拿投影答题就会答出过期话
2. §6.1 那条文案红线只约束过网关的话。宿主在屏侧，闸就管不到记录里
3. 用户明确要求在手机上看到圆屏那一侧的对话 —— 反过来（宿主在屏）就做不到这条

所以屏是**耳朵和嘴**，手机是**记性和闸**。落到线上是这几条规矩：

```
屏上按住说               手机里问                    手机主动播报
   │ dialog{dir:up}         │ 直接进记录                 │ 进记录
   │ origin:screen          │                            │
   ▼                        ▼                            ▼
  手机 AiGateway 答题 → ConversationLog（唯一事实源）→ dialog{dir:down} 回镜到屏
```

- **每一句都进同一条时间线**，不分"这轮的记录在谁那儿"。屏断线重连后不自己补历史，由手机把最后几轮重新推下来
- **镜像是不对称的**：手机起的一轮，问和答都要回镜（站在车那边的人只看见答，读不出这是在答哪句）；圆屏起的一轮，那句问话不回镜（屏自己已经画过了，再回一遍就是同一句话出现两次）。**代价说清楚两条**：① 屏和手机上的行数可以不一样，以手机那条为准；② 这条判断只看"这一轮是谁起的头"，不看连接，所以**两块屏同时接入时 B 屏看不见 A 屏那句问话**，只看见答。演示就一块屏，量产要改成按连接回镜（把 `origin` 换成连接 id）——那时候顺带要回答"两块屏的对话是不是同一个会话"，别顺手改一半
- 去重键是 `turn_id + dir`。`turn_id` 由**起头那一方**生成，另一方沿用它。**它必须全局唯一、跨重启唯一**：宿主的记录按它去重且这份记忆跨连接有效，屏那边要是用纯自增的 `s-0`，页面刷新后就从头编号，撞上旧 id 的那几句会被当重复直接吃掉，表现是"重连之后头几句问了没反应"。冒充件的做法是 `s-<开机随机段>-<自增>`
- **出站帧走 `encodeDefaults = false`，等于缺省的字段不上线**（`source: local_rule` / `origin: screen` 会被整个省掉）。所以收的一方必须自己补回同一套默认值 —— 屏那边读到一个 `undefined` 的 source，角标就会一路掉进兜底档，把"未接模型"显示成"手机起"。这条两边都要记：JSON 里省掉不等于对面知道 —— 屏那边靠它把答钉回原来那一轮。主动播报每轮都要换新的 `turn_id`（带时间戳），否则冷却后的第二轮会被去重当成重复丢掉，表现是"屏上听得见、手机里没记录"
- `dir: down` 的帧**只补记录，不再触发答题**。少这一条，屏和手机会互相把对方的话再问一遍，无限对答
- `source` 逐条标，不整块标一次。`xiaozhi_cloud` / `muse_cloud` 是同一类：那句话是**屏那侧的云**替我们说完的，**只入账、不触发我们的技能、不回镜**。把别人的输出当问题再喂一遍网关，等于让别人决定我们要不要发卫星报文。
  换到 Muse 底座以后 `muse_cloud` 是主来路（屏本机那条 ASR→云→TTS），`xiaozhi_cloud` 留着给还没换底座的那版固件。
  **屏这边要做的两件事**（组件都已经有口子，缺的是接上）：
  ① `screen_link_send_dialog_up()` 已经有了，但 Muse 那版 `carpet_page.c` 一次都没调用过 —— 于是孩子对着屏说的话，手机的时间线里一条都没有，"家长在手机上看到孩子问了什么"这条产品话现在是空的。
  ② 上行的那条 `source` 要填 `muse_cloud`，别省着不填。省了它，手机会按默认档 `local_rule` 记成"我们自己的规则答的"，那个标就是假的
- 对话帧不设 ACK、不重发。它和 `state` 一样容忍丢失：丢了这一句，屏上少一行，手机那条记录还在。**别为了几行聊天文字给对话面加一套重传**，那套的正确性成本比它救回来的显示成本贵

**当前是明文 `ws://` 而不是 wss。** 理由和补偿控制在 DECISIONS D8，一句话：圆屏侧连自签证书要引 TLS 栈并关掉校验，换来的实际安全性接近 0，工程量却会把 W2 吃掉。补偿是「默认拒绝接入 + screen_id 白名单 + 只在演示时开」三层。量产前这条必须重评。

## 音频通道（契约 v3）

答句的文字早就上屏了，这一档加的是**那句话的声音**：合成在手机（或彩排台那台 PC）做完，
裸 PCM 分块推到屏，屏放喇叭、口型跟着真实能量走、答句分页跟着播放位置走。

```
答句 → dialog{dir:down}（文字，先发，独立成帧）
     → TTS 合成 16k/单声道/s16le → 2560 字节一块 → command{cmd:audio_chunk, args:{turn_id,seq,total,rate,b64}} × N
```

- **为什么骑在 `command` 上而不是新开一种 `t`**：组件收到不认识的 `t` 是**关连接、一句话不说**，
  收到不认识的 `cmd` 只是丢这一帧。新开一种帧类型等于要求所有屏先升到 v3 才不掉线 ——
  那是把加性修订做成破坏性修订。这条是整个 v3 里唯一不能反过来决定的决定。
- **为什么不走单独的 UDP 面**（远端那版架构 A.4 #4 提的那条）：它解决的是持续音频流（语音通话、
  几十秒以上），我们推的是两三秒的答句片。三条理由：① 音频这一档实际需要约 **22 KB/s**
  （3.5KB 的帧装 0.16 秒声音），量级上跟 1 Hz 的 state 差十倍但仍是小数目，犯不上为它开一个面；
  ② 这台 PC 上没有 MP3/Opus 编码器，只有 .NET 自带的 `System.Speech`，它给的就是 PCM/WAV；
  ③ 一条链路一套心跳、一套重连、一套白名单。多开一个端口在展台上多一种"另一条没放行"的死法。
  **说清没称过的那一半**：这条 ws 的持续入站吞吐没实测过 22 KB/s，第一次跑 `--voice` 时要看屏侧
  `@audio … drops=` 那条计数 —— 不为 0 就说明这条路的带宽还没证。
  **音频流真要上屏（通话、长段播报）时这条要重评**，届时按 4KB 帧的限制算预算，别默认还能沿用。
- **帧预算是硬的**：`SCREEN_LINK_MAX_FRAME 4096` 同时是 `ws_cfg.buffer_size`，入站帧超了这个数直接丢。
  2560 字节 PCM → base64 3416 字符 → 整条约 3.5KB。core 侧 `AudioChunks.JSON_LIMIT = 3800` 逐帧断言，
  超了整段返回空列表（**合成再长也不会撑爆屏**）。
- **降级只有"没声音"这一种**：`seq` 不连续 → 整段丢掉（半段声音是"这句话讲了一半卡住"那种现场事故）；
  `total` 超 **2 MB（=64 秒）** → 整段丢掉；`turn_id` 变了 → 清缓冲重来；断线 → 立刻 abort。
  **文字答句走 dialog 那一帧，跟这里没有任何依赖** —— 语音失败永远扣不下答句。
  这个 2 MB 是 2026-11-06 从 512 KB（=16 秒）提上来的：屏的 PSRAM 实测 8 MB
  （开机日志 `octal_psram: density 0x03 = 64 Mbit`），答句整段装得下就别切半段。
  **发送侧 `AudioChunks.MAX_TOTAL_BYTES` 和固件 `carpet_audio.c` 的 `AUDIO_CAP` 是同一个数，
  改一个必须改另一个** —— 两边不一致的表现是"发送侧觉得装得下、屏侧装到一半开始丢"，
  而那正好是这条要防的"半句有声音半句没声音"。屏侧那一半**还没上板称过**：
  `>carpet` 的 `@audio` 那行现在多回 `cap=… psram_free=… psram_max=… 装得下 N 秒`，刷完先看那行。
- **协商**：`hello.protocols` 报 3 才发音频。发送侧先看 `ScreenLinkServer.audioReady`，
  对面不报 v3 就连 TTS 都不跑（白跑一遍是白等一秒），只留文字。

### v3 另外三项（都是可选加性）

- `ui.card = maint`：`docs/MAINTENANCE.md` M3 那一档。**一行该做的事，不带数字、不带判据**。
  屏侧要的是"未知档退回 `status`"，所以老固件收到 maint 不会画坏，只是不画。
  **那句文案不加新字段**（2026-11-06 拍板）：它骑在现成的 `dialog{dir:"down", skill:"maint"}` 上，
  归类靠 `skill`；屏收到 down 就走答句那同一条路念出来，`maint` + `worried` 只决定脸和那一枚琥珀点。
  详见 `firmware/screen/HANDOFF.md` §3(A) 与 `firmware/screen/muse/README.md` §5.4.1。
- `hello.screen{w,h,round,touch,ppi}`：面板几何。服务端要按屏的实际尺寸排版，而这套契约里
  **唯一知道尺寸的只有屏自己**。`w` 或 `h` 传 0 = 整项不申报 ——
  别填一个看着像真的的数，那会让对面按错的宽度排版还一切"正常"。

- `command{cmd:"wake"}`：把熄了屏的圆屏点亮，落地的是 POWER 键自己那条路（不是更轻的一条）。
  契约上它和 `audio_chunk` 是同一种东西 —— **骑在 `command` 上、不新开 `t`**，理由见上面那条
  "唯一不能反过来决定的决定"；老固件收到 `cmd:"wake"` 只会丢这一帧，不掉线。
  **不带参数**（`args` 可有可无，屏不看）；**不回 ack、不重试、不排队** —— 屏醒了下一步会自己
  发 `state`、`page_report` 和那条 `hello`，那些才是"叫醒了"的证据。手机侧要按**没叫醒**处理：
  发出去 3 s 内没看到这条连接上有任何动静，就当这一下没成，别静默。
  什么时候发：手机侧的唤醒词命中，或用户点「叫醒圆屏」。**答句不要额外发这一条** ——
  `dialog{dir:"down"}` 在屏侧本来就会点亮屏幕。
  **硬前提：那条 WebSocket 还活着。** 屏在电池上熄屏到点会 `nap`（Wi-Fi 关掉，见固件
  `muse_input.c` 的 `WIFI_NAP_MS = 2 分钟`），那一刻连接就没了，这一帧送到空气里，
  只有按 POWER 能叫醒它。所以这一条只在设置页「熄屏后保持联网」开着时才有效；
  App 侧的要求写在 `docs/APP-SCREEN-CONNECT.md` 第十节。

## 上行音频通道（契约 v4 · 设计，未实现）

「对着屏说话」才需要这一档。屏已经是嘴（`audio_chunk` 放音），这一节给它装耳朵：屏采的裸 PCM
推到手机，手机做转写，答句照旧走 `dialog{dir:"down"}`。方向反过来了，但帧的形状**刻意和 v3 下行做成同一套**——
同骑 `command`、同一组 `args` 键、同样 2560 字节一块，只为让两侧只剩一套分块代码。

```
按住（屏生成 turn_id = s-<开机随机段>-<自增>，此后这一轮所有帧都用它）
     → command{cmd:mic_chunk, args:{turn_id,seq,total,rate,b64}} × N   每 80 ms 一帧
     → 手机转写 → dialog{dir:"up", turn_id:同一个, text:转写出来的那句}    这句是屏该显示的
     → 手机照旧答 dialog{dir:"down"}（+ 可选 audio_chunk）
```

- **`turn_id` 由屏在按下的那一刻生成，手机不许另起一个。** 它是这一轮的唯一编号：`mic_chunk` 靠它拼段，
  `dialog` 靠它去重，答句靠它配对。手机换号的表现是"声音和文字对不上、同一句话画两遍"。
  上行那句走 `dir:"up"`，语义仍按对话面那套 —— 它是**记录**，不是请求手机重答一遍。
- **为什么又是 `command` 而不是新开 `t`**：和 v3 那条"唯一不能反过来决定的决定"同一条理由，一字不改。

### 第一条要求不是音频，是「让屏先知道对面是几版」

v3 那句「收到不认识的 `cmd` 只是丢这一帧」**只在屏那边成立，手机那边正好相反**。
`CommandType` 是 Kotlin 严格枚举（`core/.../protocol/ScreenLink.kt:112`），枚举外的值在
`ScreenMessage.decode` 里抛 `SerializationException`；入站解码整个包在 `runCatching` 里，失败分支是
`conn.close(CLOSE_POLICY, "bad contract")`（`core/.../screen/ScreenLinkServer.kt:97-102`），
而且 `Json { ignoreUnknownKeys = true }` 救不了枚举取值 —— 它只管多余的键。
**所以对着现在装在手机上的 v3 App 发一条 `mic_chunk`，表现是链路当场被手机关掉、一句话不说**，
和「App 无法连接圆屏」那两次现场故障同一个观感。

屏又**没法自己算出对面是几版**：协商号是服务端算的，`ack` 帧里没有版本字段可以回读，
固件只能取自己申报的那一档（`components/screen_link/screen_link.c:59-63`，
`s_negotiated = SCREEN_LINK_CONTRACT_MAX`）。这条不对称是 v1 时就写进注释的已知代价，
上行音频正好踩在它上面。

所以 v4 的第一条是**加性地把协商号回读**：

- `AckPayload` 多一个可选整数字段 `protocols`（`ScreenLink.kt:433`），hello 的回执里带上服务端
  实际支持的档位。老固件用 cJSON 读 ack，多出来的键直接看不见，不掉线。
- 固件收到后**只用它给"上行"这一路把闸**：申报号缺失或低于 4 时，屏不许发任何 `cmd`。
  **不要拿它去覆盖现有的 `s_negotiated`** —— 那个变量现在管的是 `screen_link_dialog_ready()` 这类
  "屏能不能说话/能不能收"的判断，而收这一路对着老 App 本来就是安全的、已经跑着的；把它清零换来的
  是一台好使的屏突然连答句都不画了。风险是不对称的：**下行错了屏只是丢帧，上行错了手机关链**，
  所以这道新闸只管上行，别的都不动。
- **没有这个键就当"不许上行"**。这里"缺了 = 不发"是安全默认，
  和 `SatState.module_ok` 那条"缺了必须当不知道"的反面教训不冲突 —— 那条是显示字段，省略会被读成假值；
  这一条控的是**发不发**，误判方向是沉默而不是炸链。
- **发布顺序是硬的，不能倒**：先让 App 会申报、并且认识 `mic_chunk`，装机之后才允许固件发这一帧。
  反过来的话，一块新固件能把一台没更新的手机当场踢下线，那比"屏不能说话"重得多。

### 帧预算与屏侧的取数位置

- 采到的就是现成的：`idle_capture()` 每 20 ms 从 `muse_audio_read` 拿 320 帧（16k/单声道/s16le = 640 字节），
  喂 `s_pre` 预滚环和设置页那个音量条。**2560 字节 = 4 个 20 ms 块 = 80 ms** → base64 3416 字符 → 整帧约 3.5 KB，
  压在 `SCREEN_LINK_MAX_FRAME 4096`（同时是 `ws_cfg.buffer_size`）里，和 v3 下行同一个数。
- **12.5 帧/秒 ≈ 43 KB/s 的入站 JSON**。下行那条文档里写了"22 KB/s 没实测过"；上行这条更糟，
  是**手机作为服务端从没被这块屏压过任何持续入站流量**。第一次真跑要在手机上看到收帧序号连续，
  在屏上看到发送侧没有阻塞。
- **不许在 `voice_task` 里直接发帧**：那条任务的 20 ms 读取就是它的节拍，`esp_websocket_client_send_text`
  一旦因为 tx 队列满而阻塞，掉的是**采到的音频**而不是某一帧。要做的是生产者/消费者切开：
  `voice_task` 写 PSRAM 环，独立上行任务取环、组帧、发。环满了丢什么必须先写死再实现 ——
  按 v3 下行那条同款的规矩，**整段作废比"后半句没了"好**，但上行的整段作废意味着这一轮白说，
  所以屏侧要给一个"这轮没送出去"的反馈，别静默。
- 「按住说」8 s 上限 = 256 KB PCM = 100 帧。和下行那个 2 MB(=64 s) 的段上限是两个数，别混。

### 屏侧现状：那条「录音通路坏了」要先改判

之前量到的"自测过了（-54.9 dBFS）之后所有 `muse_audio_read` 全失败"，
现在有一个**更便宜的解释，而且它把结论翻过来**：

- 那句 `i2s_common: i2s_channel_read(1410): The channel is not enabled` 不是状态位，是**拿令牌的超时**。
  IDF 那边读一次要借一次二进制信号量，通道 enable 时给、disable 时收（`i2s_common.c`）；
  esp_codec_dev 读默认等 1000 ms。所以任何**第二个读者**都会等满 1 秒、然后打这一行一模一样的错。
- `muse_audio_read` 自己不加锁（锁只在 `muse_audio_power` 里），所以两个读者就是纯竞争。
- `voice_task` 在不 rest 的时候**每一圈都在读麦克风**（`idle_capture()`，注释写着"The 20 ms read paces this loop"），
  而 `rest = asleep && battery`。**在 USB 供电的台子上 rest 永远为假**，也就是说麦克风一直是被 voice_task 占着的。
  我之前那个从串口任务发起的探针，正是撞上去的第二个读者。
- 顺带把"强制 `muse_audio_power(false)` 卡住"也解释了：`Pending out channel for in channel running`
  是配对逻辑在等一个被在途读者拿着的令牌（`portMAX_DELAY`），不是硬件坏了。

**这条 2026-11-10 已按上面的判据称到，改判成立**：进设置页声音那一栏，对着麦克风拍手 ——
**电平条和 dBFS 数字有反应**（owner 实测；他没说当时插没插 USB，但这一条判据和供电无关：
`rest` 要 `asleep && battery` 同时成立，而那一页亮着屏，所以两种供电下 `voice_task` 都在读）。
所以**屏侧的录音通路本来就是好的，没有 bug 要修**；
之前那句 `The channel is not enabled` 是串口探针自己撞上了 `voice_task` 的常驻读取（第二个读者等满 1 秒令牌）。
推论直接落到实现上：**上行不许新开读者，就在 `voice_task` 里取它已经拿到的那 20 ms 块**（`s_chunk` / `s_pre` 那条现成的路）。

还剩只有代码量出来才知道的那一半，别当成已定：稳态下谁持有令牌、以及 `s_open` 有没有被某次
`set_fmt` 的内部 disable 留在错状态 —— 这两条在上行真跑起来、开始和放音撞车之前不用管，撞车那天要管。

- **16 kHz 单声道 s16le 封成 WAV 它认，字准，用时不到一秒。** 这一条以前是"估的"，现在是称到的。
- **必须封 RIFF 头，而且它嗅容器不看后缀/Content-Type**（`.wav` 名字装裸 PCM 照样 500，

  但屏侧到点必须给一个"说完了/被截断了"的可见反馈，否则用户以为是自己没说清。

**限流/配额**：连打 4 次全 `200`（0.34 / 0.37 / 0.38 / 0.46 s），同时打 3 个全 `200`（0.43 / 0.53 / 0.64 s），

**但这不等于"没有日额度"** —— 免费档的天花板在账号侧，连着打十次称不出来，

  `ConnectionResetError [WinError 64] 指定的网络名不再可用`，而同一次 DNS 正常（`150.171.28.10`）、
  对照请求硅基流动也通（401）⇒ 不是网络断了。**原样重试一次就全过**（上表是重试那次）。
  **音色写死，不要调 `list_voices`**，少一个会抖的请求
- 代价不变：非官方端点随时可能变、现场必须出网、出的是 MP3 要解码重采样切块（系统 `MediaCodec`，APK 不长大）

**压缩答句 = 靠提示词压，不靠砍 `max_tokens`。** 同一句问句加 system
（`你是车载卫星助手。用一句话回答，不超过30个字，直接给结论，不要解释推理过程。`）、`max_tokens=200`，打 hanbao：

| 模型 | 用时 | 答句字数 | completion tokens（其中思考） |
| --- | --- | --- | --- |
| **`deepseek-v4.1-flash-1017`** | **3.05 s** | 20 | 158（**145 是 reasoning**） |
| `glm-5.3-flash` | 3.67 s | 25 | 53（35 是 reasoning） |
| `deepseek-v4-pro` | 6.61 s | 23 | 15 |

- 对比不加压缩提示那轮的 3.9~10.1 s ⇒ **最快那一档压到 3.05 s**，整条因此收窄到 5.6~6.4 s 才出声
- **`max_tokens` 要给到 250 以上**：20 字的答句实测烧掉 158 个 completion token（145 个是思考），
  给 120 会截断、然后推理草稿漏进正文（前面已称过）。**长度由提示词约束，不由配额约束**
- **"不要解释推理过程"只压正文、压不掉内部思考**（145 个 reasoning token 照烧）⇒ **3 s 是这条对话面的地板**，
  再快要换模型或上流式，那是下一次决策
- **这轮没喂事实表**（真 App 里 `facts = { aiContext() }` 会喂），所以内容不代表真实表现：两档 flash 都回
  "需提供卫星编号和当前位置"，而 **`deepseek-v4-pro` 直接编了个「预计 5 分钟后过顶」**。
  ⇒ **选 `deepseek-v4.1-flash-1017`**（最快，缺数据时要数据而不是编数据）；
  这条也正好说明文案红线为什么必须在出口 —— 模型会编"几分钟后/已送达"这类句子
- **工作上限按字数卡：一句、≤30 字。** 晓伊语速约 4 字/秒，17 字仍有 4.3 s 播放时长，
  所以"看起来短"不算短；压缩同时省的是播放时长、下行帧数、流量三样

### 还没称过的（别按已实现讲）

- 43 KB/s 入站：一次都没压过
- `mic_chunk` 的失败模式：v4 的申报回读落地前，它是**会关链的**，不是会丢帧的
- 云转写在展台上的可用性：**蜂窝已答（走）**；**端点也已称（2026-11-10，owner 给了 `https://hanbao.party/v1`）** ——
  结论是**这家没有语音**：`GET /v1/models` 回 200 只有三档对话模型（`deepseek-v4-pro` /
  `deepseek-v4.1-flash-1017` / `glm-5.3-flash`），`POST /v1/audio/transcriptions`、`/v1/audio/speech`、
  `/asr`、`/stt`、`/tts` 全部回 `404 page not found`，**和随手编一个路径的回话一字不差**；
  同一次探测里 `/v1/embeddings` 和 `/v1/messages` 回的是 `400`（说明路由存在、只是 body 不对），
  所以那六个 404 是"真没有"，不是"方法不对"。**ASR 的落点已经另找了一家并称完**（硅基流动，见上面
  「转写端点实测」）；**hanbao 仍然是对话面那一家，不换** —— 两家分工：它答话，硅基流动听写
- **顺带称到的、和音频无关的一条**：这家对话面单次实测 **3.9 ~ 10.1 秒**（同一句中文问句，三档模型；
  最长那次是 `glm-5.3-flash` 拿 220 token 配额、其中 20 花在思考上），而 App 那边
  `OpenAiCompatProvider` 的读超时写死 `Duration.ofSeconds(12)` —— **答句稍长一点就当场超时**，
  而且推理型那两档在小 `max_tokens` 下会把英文思考草稿当成正文吐回来。**这一条不依赖 v4，现在就该修**
- 端到端时长：**分量都称到了，但整条串起来没称过**。按 owner 拍的压缩答句 + edge 晓伊那一档相加：
  转写 0.6~0.8 s + 对话面 3.05 s + 合成 1.9~2.5 s ≈ **5.6~6.4 s 才开始出声**，然后放 4.3 s（17 字答句）。
  算式而已。手机蜂窝上传 256 KB 要多久也没称过
- 屏上采集与放音同时进行（回声、以及同一根 I2S 总线上的双向）：**没碰过**

## 保活与断线

- App 每 1 Hz 发 `state`，这本身就是心跳。**3 s 没收到 state，展示端把链路图标变灰**；10 s 没收到则重连
- 展示端不主动发心跳，省流量省电
- 重连退避：1s / 2s / 5s / 10s / 30s 封顶
- **上面那一条是"socket 拨不上"。还有一档是"socket 还没开始拨"**：客户端句柄建不出来
  （2026-11-10 真机：开机那几十秒内部 RAM 最紧，`screen_link_start: ESP_ERR_NO_MEM`）。
  这一档以前是**一次性的** —— 建不起来就不再有任何一条路会去建，屏挂着网、地址对、
  服务端活着，却永远不发 `hello`，App 那边只看到"连不上圆屏"。
  现在按 5s / 15s / 30s / 60s 封顶重新建一次（`carpet_link.c` 的 gate），
  且每次重建前把上一轮的句柄、队列、事件组全部退回去 —— 不退的话第二轮只会撞
  `ESP_ERR_INVALID_STATE`，"重试"变成空壳。对 `hello` 什么时候到，App 侧不需要做任何配合。
- 断线期间展示端**保留最后一帧 state 并打灰色水印「链路中断 mm:ss」**，不要黑屏。演示时黑屏等于事故。
  数据保留最后一帧，但**卡面**连续 10s 没声就落回钟面 —— 理由和边界见下面「断链够久」那一节

## 可靠性

- `event` 必须回 `ack`（带 `for_event_id`）。App 3 s 未收到 ack 重发一次，再 3 s 放弃并记日志
- `state` 不重发、不去重，靠 `seq` 单调递增检测丢帧。丢了无所谓，下一秒就是新的
- 展示端按 `event_id` 去重，保留最近 32 个 id（环形缓冲，够小）。**这个环跨重连不清空** —— 屏不重启它就一直在。所以 id 必须**全局唯一**而不是"本次进程唯一"：App 重启后 seq 归零，`evt-0..evt-31` 会整批撞上屏上还留着的老 id，被当重复静默丢掉，丢的那条可能是 `sos_acked`。两侧各自的写法：App `evt-<启动标签>-<seq>`、屏 `scr-<启动标签>-<seq>`；长度上限 39（屏侧 `EVENT_ID_MAX` 减一，超了 `strncpy` 截断，两个 id 会共用一段前缀）

## 页面归屏、内容归手机（2026-11-04 两台机器商定）

这一节改的是**权**，不是字段。定下来的四句话：

| | 归谁 | 走哪条 |
|---|---|---|
| **在哪一页**（L0 脸 / L1 选场景 / 车载 / 亲子 / 数字分身 / 时钟 / 图片） | **屏** | 触摸直接切，不等手机往返；切完通报一条 `page_report` |
| **这一页里说什么**（卫星倒计时、答句、状态总览、那张脸） | **手机** | 还是 `state.ui.card` / `ui.emotion`，1 Hz 那一帧 |
| **盖住一切的那件事**（SOS 确认 / 平台回执 / 越界） | 手机发起，**屏执行** | `event`；这是唯一允许服务端抢占的一档 |
| **谁在跟谁说话**（每一轮问答） | **手机**（唯一事实源） | `dialog`，见上面那节 |

为什么这么切，三条都成立：

1. **一次触摸不能等一个往返。** 页是手上那个动作的直接后果；绕手机一圈，快的时候 200ms、
   链路刚掉的时候 30s —— 后面那一种是"屏按了没反应"，而这正是我们已经在 #36/#42 修过两轮的那类现象。
   内容不一样：内容由**车里正在发生什么**决定，而那些事全在手机那台状态机里。
2. **两侧各自定页会讲两件事**这件事不成立，各自定内容才成立。页是本地可见的（玻璃上就是它），
   内容是要判断的（该说倒计时还是该说越界）。判断权留在有事实的一侧，翻页权留在有手指的一侧。
3. **手机上那块镜像必须跟着页走。** 首页那枚圆画的就是推给屏的这一帧；屏已经在亲子页、
   手机上还写着"屏在状态盘"，观众先怀疑的是屏坏了 —— 所以回声这一档不是可选项。

### `page_report` 是通报，不是申请

这条区别是**整套分权的全部代价所在**，两边都要写进代码而不只是文档里：

- 屏切完页发 `command{cmd:page_report, args.page:"kids"}`。**手机不许驳回、不许改判**：
  `DemoRuntime.reportScreenPage()` 只做两件事 —— 认得出就存下来并回声进 `state.ui.page`，
  认不出就记一行日志、值不动。
- 认不出来的页名**一律拒收**（`ScreenPage` 就那七个）。这条不是防御性代码：Muse 底座自己那套
  tile 里就有 `settings` 这个名字，将来底座加一页而契约没跟，表现是屏自己切过去了、
  手机上那一格静默停在上一页。所以 `:core` 有两条断言钉它（`ScreenCommandTest`）。
- **组件那道闸已经放行**：`screen_link.c` 的 `ALLOWED` 里加了 `page_report`。
  固件那边不用改闸，只要发。
- `card_set` 和 `page_set` 都不在契约里，是**刻意**不在：前者会把内容判断权下放给没有事实的一侧，
  后者会把刚交出去的翻页权又要回来。`SchemaDriftTest` 两条都拦。

### 手机上那一格读什么

`DemoRuntime.Status.screenPage`。null 有两种，都不许用旧值填：
**老固件不会报**，和**屏刚重连还没补报**（屏断线时手机会把它清成 null —— 屏不在了还写着
「屏在亲子」是那块镜像能编出的最贵的一句假话）。App 首页对应文案是「屏没报它在哪一页」。

**这一个字段还多用了地方**：屏说上来的那句话归手机哪一页，是从它换算的
（`vehicle → 车辆页`、`kids → 家人页`，其余页名不归任何一页，只进首页那条总时间线）。
所以漏报的代价不只是镜像空一格 —— 是**屏上说的话在手机上找不到它该在的那一页**。
归页这件事本身写在 `docs/DECISIONS.md` D11。

### 屏重连之后必须补报一次

`page_report` 只在**页真的变了**的时候发。少了补报，重连之后手机上那一格会一直空着，
直到下一次真的翻页才复明。所以建链成功（`hello` 发出去）之后要立刻报一次当前页 ——
`simulator/screen.html` 已经按这个跑，固件那侧对应 `screen_link` 的 hello 之后同一个调用点。

### `dialog.action`：语音拉起场景，只跳页

```
家长在屏上说"给孩子放首歌" → dialog{dir:up, source:muse_cloud}
  → 手机答题 → dialog{dir:down, text:"…", action:kids}
  → 屏翻到亲子页，再回声一条 page_report{kids}
```

- **只允许挂在 `dir=down` 上**，挂在上行会被手机端剥掉（屏不能给自己下命令，那条边界不许绕过）。
- **只做换页这一件事**：它不是技能口、不是 SOS 口。所以"云端代答的一句话替车主按下了呼救"
  在这条契约里构造不出来 —— 这也是为什么它值得挂在已经存在的对话帧上，而不是新开一种帧。
- 对话面不重发。丢了这一条 = 屏停在原页、手机记录仍在，这正是要的降级。
- **生产者还没有**：跳页要靠命中的技能给出一页，而 `:core/ai` 技能表里现在七条全是卫星/车辆那一路。
  亲子那一条进来之前，这一档只有屏侧那半（`simulator/screen.html` 的 `applyAction()` 已经实现）。
  **别把它当成"已经通了"去讲**

### 版本：不升

没有新的 `t`，三个字段全是可选加性的，`hello.protocols` 里这三条仍按 v2 就能发（v3 只是又往上加了一档，
见上面「音频通道」）。老固件继续看状态、继续能对话，
只是不会报页（手机上那一格空着）也不认 `action`。这是 v0.2 的第三轮加性修订，契约号没动。

## 上行：屏只能请求，不能决定

- `command` 那三条交互用的取值（`card_next` / `card_auto` / `poke`）**都是请求**：屏只说"用户在这块玻璃上做了什么"，
  画哪一张卡、画哪一张脸仍由手机算出来写进 `state.ui.card` / `ui.emotion`。
  **这一节只管内容那一半**（见上面「页面归屏、内容归手机」）：同一根手指翻页不归这里管，那是 `page_report`
- 为什么不给屏一个 `card_set`：定卡权一下放，同一辆车就会在手机和屏上讲两件事，而 §6.1 那套文案红线只约束得过网关的那一路。
  请求制还留了一个**拒绝对**：SOS 正在 `armed`/`pending`/`sent` 的时候 `card_next` 被顶回来，
  观众不能把卫星卡滑走 —— 那种时候屏上唯一该说的话是倒计时
- `card_auto` 是手动钉住之后唯一的出口。钉住的入口有两个：App 设置页那个选择器，和屏上的左右滑
  （每一条 `card_next` 都会把卡钉在算出来的那一张上）。所以屏也必须有一条交回的路，不然滑两下之后
  这块屏就再也不跟着车里的事变了 —— 固件那侧用的是**长按卡面**（≥800ms）发 `card_auto`
- 屏发的每一条都必须过组件里那道合法值闸（`screen_link_send_command` 的 `ALLOWED`），非法值当场退回、绝不上线：
  手机端解不开入站帧的处理是**关连接、一句话不说**，屏这边只表现为"按了没反应、过几秒掉线"
- 这四张表由 `:core` 的 `SchemaDriftTest` 逐条比：schema 的 `command.cmd`、Kotlin 的 `CommandType`、
  固件的 `COMMAND_NAMES`、组件的 `ALLOWED`。
  **比不了的那一半要说清**：`COMMAND_NAMES` 在 `firmware/screen/app/main/app_main.c` 里，而那棵树
  从没进过仓库（只在写它的那台机器上）。这条断言在别的机器上是**明着 skip**，不是绿。
  Muse 那一路改比仓库里就有的 `firmware/screen/muse/muse-carpet.patch`：补丁里 `CMD_NAMES` 那三条
  必须既在 schema 里、又过得了组件那道闸。老树要真想留作回滚，就把它提交进来，别让它当"看不见的守卫"

### 这块玻璃上的手势（固件 #42）

阈值都是固件自己按按下点/松手点算的，不走 `LV_EVENT_GESTURE`：那条只发给被按住的对象，
且链路上任何一层可滚容器都会把滑动吞成滚动。60px≈5.7mm（266dpi），是"有意滑动"和"擦个灰"的分界。

| 动作 | 上行 | 本地 |
|---|---|---|
| 左右滑 ≥60px | `card_next`，`args.dir` = +1（往右）/ -1（往左） | 什么都不改，等手机的下一帧 `state.ui.card` |
| 上下滑 ≥60px | 无 | 上滑展开、下滑收起当前卡的明细层（定开/定关，不是 toggle） |
| 单击 | `poke` | 什么都不改 |
| 长按卡面 ≥800ms | `card_auto` | 什么都不改 |
| 长按那颗圆钮 ≥1500ms | `sos_press` | 进度环 |

一次触摸只认一个动作，所以本地什么都不改的手势才敢只发一条上行。

**单击不再切明细**（这一条从 #42 起改了，固件和彩排冒充件都要按这个走）：契约里 `poke` 就是单击，
而手机收到 poke 会把卡切成表情卡并留 8 秒。同一根手指既展开明细、又把整张卡换掉，
展开的那 6 行 1 秒内就随旧卡一起消失 —— 屏上看着像"我点了一下它自己乱跳"。
明细层因此改给上下滑这条确定的手势，单击只负责"我在玻璃上动过"。

### 断链够久：屏自己落回钟面（唯一允许固件挑卡的一档）

`firmware/screen/app/main/app_main.c` 的 `offline_clock_due()`：连续 10s 没听到有效 state
（连着但 >3s 没帧、或套接字断了在退避，两种算同一个数），屏就把卡换成 `clock` 本地画。
写死在契约里，是因为两侧各自猜就会讲两件事：**这是屏唯一一次可以自己挑卡，别的地方都不许。**
（"挑卡"指内容那一半。挑**页**是另一件事，那一半归屏，见「页面归屏、内容归手机」——
这一档说的不是"屏不许自己动"，是"屏不许自己决定替手机说哪句话"。）

- 为什么是钟：继续挂着一张不再更新的卫星倒计时，是在替一个已经联系不上的手机维持一句它没法负责的话；
  钟至少还是屏自己给得出的东西（停在最后一帧，钟面第二行会写"链路停了 · 停在最后一帧"）
- 为什么不是状态盘：那张盘上每个数都来自手机，断了就全是旧的，看着比钟更像"一切正常"
- 为什么阈值是 10s：和组件自己掐线重连那个数对齐，屏跟的是"这条链路已经被判定死亡"那一刻；
  比契约里 >3s 变灰晚，是因为变灰只是"可疑"，还不值得换掉整块屏在说的话
- 一次都没连上过（`seq==0`）**不走这档**：那时钟面只有 `--:-- 还没有一帧`，
  而状态卡那句"等手机接入"才是观众能照着做的事
- 链路恢复后手机的第一帧 `state.ui.card` 立刻把卡抢回来，不需要屏做任何决定

## 安全边界

这套服务能读车主位置，而现在是明文传输、无认证。所以：

- 监听 `0.0.0.0:8443`，但 `accepting` 默认 false —— App 上不打开了「允许展示端接入」，任何连接进来立刻 close。这比 bind 127.0.0.1 弱一点（端口对外可见），但省掉了「演示现场还要先进设置页改绑定地址」这条必错路径
- `hello` 必须携带预共享 `screen_id`（出厂烧录，App 侧白名单），不在白名单直接断
- 关掉开关时**主动断开已有连接**，不是等它自己超时
- **对话面上的是同一条明文链路**，所以那个开关现在的含义变重了：它不只放开位置，还放开车主说出去的话。演示现场AP尽量自己开，不要连商场地场的公共 Wi-Fi
- 红线一（§6.1）在两侧各守一次：手机过闸后才入记录，屏在画出来之前再过一次。**屏那一次不是重复劳动** —— 小智官方云那条路是它自己往屏上画的，手机的闸管不到，而现场冒出一句「救援已在路上」是不可挽回的那种错
- 演示结束后关掉，或 App 退出即关（`MainActivity.onDestroy` 里 `shutdown()`）
- 不要把这套服务部署到公网。**任何情况下都不要。** 需要远程查看就等真正的业务后端
